# AGENTS.md

Context for anyone — agent or human — editing this project.

## What this is

An internal tool suite for BOLD Lab's paper-submission process, built as an **implementation of BOLDiquette § ML Conference Cycle** — and, ahead of BOLDiquette, of the real pre-submission runway the lab runs (register 8 wk out · Pitch Day 6 wk · first draft + Internal Review 4 wk · final draft 2 wk · PI approval 1 wk · submit). Three self-contained HTML pages (plus an `index.html` redirect stub) and tracking docs. No build step, no framework — a Firebase backend (Firestore/Auth/Storage) as of 2026-09-11, everything else still plain HTML/CSS/JS.

**Layout, reorganized 2026-09-11:** the served pages and Firebase config stay at repo root (GitHub Pages serves from root; `firebase` CLI expects its config there by default). Contributor-facing docs live in `docs/`.

## Running it

```
python3 -m http.server 8137
```

Then open `index.html` (redirects to `how-to-submit-a-paper.html`), or any of `how-to-submit-a-paper.html`, `audit-board.html`, `diff.html` directly. `how-to-submit-a-paper.html`/`diff.html`/`index.html` also work opened as plain `file://` pages. `audit-board.html` needs to be served (not opened as a bare file): it talks to Firebase (Firestore/Auth/Storage), and Sign-in-with-Slack's popup flow needs a real `http(s)` origin.

**`audit-board.html` talks to real production Firestore by default** (`FIRESTORE_USE_EMULATOR = false`, `AUTH_USE_EMULATOR = false`). For local dev against a disposable local Firestore instead (e.g. testing something that writes data you don't want landing for real): run the Firestore emulator (`firebase emulators:start --only firestore`, needs a JVM — see `docs/FIREBASE.md` for the portable-JDK workaround used when Homebrew's `openjdk` won't install), flip `FIRESTORE_USE_EMULATOR = true` locally, and don't commit that. `AUTH_USE_EMULATOR` can stay `false` even then — the emulator accepts real Firebase Auth ID tokens fine, and the local Auth emulator doesn't have the `oidc.slack` provider anyway. **This flag shipped wrong once already** (committed `true`, silently broke the live site for anyone without a local emulator running, caught 2026-09-11 when a real second user hit it) — double-check both are `false` before committing/pushing. There's now also a loud, hard-to-miss red banner (`#emulatorWarning`/`.emulator-warning`) that shows across the whole page whenever `FIRESTORE_USE_EMULATOR` is `true` — a safety net so a repeat of that mistake would be immediately visible on the live page, not just catchable by re-reading the source. Toggled once, right next to the flag itself, not tied to any render function.

## Deployment

Every push to `main` deploys automatically — GitHub Pages' own "Deploy from a branch" source (`main`, `/`), no workflow file, nothing to run by hand. (Briefly switched to a GitHub Actions-based deploy on 2026-09-11, reverted the same day back to the plain branch deploy.) Live at <https://bold-lab-ai.github.io/bold-os/how-to-submit-a-paper.html>.

**New work happens on a branch, not directly on `main`, as of 2026-09-11.** The site is live and in real use now — every feature up to and including this point in the day shipped straight to `main` (each push deploys immediately, and several changes this session also deployed live Firestore Security Rules alongside the client code). From here on: build and commit on a feature branch, get it reviewed/tried, then merge to `main` — merging is what deploys, since there's no separate staging environment. A **Security Rules** change on a branch is not itself live until someone explicitly deploys it (`firebase deploy --only firestore`) — deploying rules and merging the matching client code to `main` should happen together, in the sequence the rules change's own docs/FIREBASE.md section calls for, not the rules going live first on their own.

## Constraints

- **No Claude / Claude-Artifacts dependency.** Never depended on Claude's artifact-storage API; the Internal Review Board persisted to per-browser `localStorage` at first, then moved to a real shared Firebase backend (Firestore/Auth/Storage, `bold-d7ff2`) on 2026-09-11 — see `docs/FIREBASE.md`. `loadBoardsIndex` / `saveBoardsIndex` / `loadBoard` / `saveBoard` / `deleteBoardData` is still the seam every caller in the file goes through; only what's behind those five functions changed.
- **External resources: Google Fonts, the Firebase SDK, and KaTeX, on `audit-board.html` only.** Everything else — CSS, JS — is inline. No bundler, ever. The Firebase exception (approved 2026-09-11, see `docs/FIREBASE.md`) is the **compat build** from `gstatic.com`, pinned to an exact version, e.g. `https://www.gstatic.com/firebasejs/10.14.1/firebase-app-compat.js` — deliberately the compat (non-module) build so it loads as an ordinary blocking `<script src>`, matching the file's existing classic-script style, rather than the modular/ES-import build (which would need `type="module"` and its deferred-execution timing doesn't mix cleanly with the page's plain IIFE). The KaTeX exception (approved 2026-09-18, per Eduardo) is for rendering LaTeX pasted into a card's Abstract field — `katex.min.css` + `katex.min.js` from `cdnjs.cloudflare.com`, pinned to an exact version, e.g. `https://cdnjs.cloudflare.com/ajax/libs/KaTeX/0.18.7/katex.min.css`; see `renderAbstractHtml()`. Bump either pinned version deliberately, not silently.
- **Every page keeps a no-JS fallback.** The guide stacks all phases; the review page stacks both parts. Don't break these.
- **Design tokens match bold-lab.ai** (the pages are meant to live at `https://bold-lab.ai/`). Each `<style>` opens with the same `:root`: `--ink:#09111f`, `--ink-soft`, `--muted:#667085`, `--paper:#fbfaf6` (page), `--surface:#fff` (cards/columns/inputs/modals), `--wash:#eef2f4`, `--line:#d8dee6`; accents `--blue` (links + primary buttons), `--teal` (Format + eyebrows), `--plum` (Science), `--amber` (attention); `--focus:#c87912` (amber focus ring); `--radius:8px`. Headings are Inter `font-weight:760`, `letter-spacing:0`. Eyebrows: uppercase, **no** letter-spacing, teal. No serif, no middot-joined meta strings, no trailing `→` on non-directional links. `audit-board.html`'s `:root` also re-defines the legacy names its inline JS styles reference (`--accent`, `--accent-dim`, `--neutral-bg/-text`, `--warn-*`, `--success-*`, `--danger-*`) — keep those.
- **Names are unified as "Internal Review" / "Internal Review Board" / "reviewer".** `audit-board.html`'s filename, CSS classes (`cl-*`, `card-*`), and JS identifiers keep their old spellings on purpose — renaming them is churn with migration risk and no user benefit.

## Editing guidelines

1. **It implements BOLDiquette.** Any place the process differs, record it in `docs/DIFF.md` with a proposed BOLDiquette change. **Never** put "this differs from BOLDiquette" commentary in the pages themselves. **Editing `docs/DIFF.md` means also editing `diff.html`** (the rendered page the three `.page-source` links point at) — there's no build step, so keep the two in sync by hand: same items, same order, same wording.
2. Each page carries **one** BOLDiquette citation (the guide's is a `.page-source` line under the title; the review page and board use `.page-source` too), ending `&middot; current differences in <a href="diff.html">DIFF.md</a>`. No per-phase source lines.
3. **Copy is terse.** Descriptions (`meta`/OG + hero ledes) are one or two sentences. No throat-clearing, no narrating process or rationale, no knowing-aside / internal-monologue lines. Only what the reader needs to act.
4. Keep an element only if removing it would make the page worse.
5. **Changing phases** (`how-to-submit-a-paper.html`): update the TOC `href`s and labels, each `<section>`'s `id` and `.phase-num`, the `.timeline` rail (`<li>` per phase, `--n` on the `<ol>`, `is-pivot`/`is-after` classes), the pager's static `Phase 1 of N`, and any cross-references (`(Phase 6)`). The JS derives the pager from the TOC hrefs; timeline links are wired via `links.concat(tl)` and synced in `showPhase`.
6. **Board columns mostly mirror the guide's phases — but not one-for-one any more, and worded differently on purpose.** Current `STATUS_ORDER` (6 keys, 2026-09-18+3): `register`, `pitch`, `abstract`, `rebuttal`, `camera_ready`, `conference` — `paper`/`arxiv` collapsed into `rebuttal` this same round (arXiv posting is no longer a gate or a column, just a link addable any time — see that change's own commit and `audit-board.html`'s `STATUS_ORDER` comment). The guide (`how-to-submit-a-paper.html`) still has **8 phases**, one more than there are statuses: Register, Submit pitch, Submit the abstract, Submit the paper, **Post to arXiv** (the one deliberate exception — a real, useful page with no `STATUS_ORDER` key of its own, pulled out of the guide's own Previous/Next pager via `OPTIONAL_IDS`/`steppableIds()` in its inline script, reachable from the TOC but not counted in "Phase N of M"), Submit rebuttal, Submit camera-ready, Accepted. Every other phase still maps to a real status, same order — adding, removing, or reordering one of *those* without the other is still a bug. `STATUS_LABELS` is deliberately **past tense** — Registered, Pitched, Abstract in review, Rebuttal, Rebuttal Submitted, Accepted — because a column names the checkpoint already met to be sitting in it (see guideline 11's gates), where the guide's headings are instructional ("Submit pitch", "Submit the abstract") telling you what to go do. Same phase, two label styles for two different jobs; don't try to make them match verbatim. Change `STATUS_LABELS` / `STATUS_HINTS` (the "move a card here when…" line under each column title) text freely. Changing a `STATUS_ORDER` **key** rewrites stored data — any card already at that status is orphaned to the "Other" column. If you must, add the old→new mapping to `STATUS_MIGRATIONS` so existing cards migrate on load — and remember that lookup is a **single hop, not chained**: if an *existing* migration entry targets the key you're retiring, repoint it straight at the new key too, the same round this bit when `paper`/`arxiv` were retired and `submitted`/`withdrawn`/`submit`/`arxiv_publicity` all had to be repointed at once (and, if the old status carried information a rename alone would lose, set the matching field in `normalizeCard()` too — see `STATUS_OUTCOME_MIGRATIONS` and the `changes_requested` case for the pattern). `.columns`' `min-width` (240px × columns + 1px × gaps + 2px border) is computed in `renderColumns()` from however many columns are actually rendering, not hardcoded — Rush mode (below) is exactly why that stopped being a fixed number.
   **Rush mode, added 2026-09-11 — the other deliberate exception.** A per-venue toggle (`board.rushMode`, a one-click button in the venue header, not a field in the Edit-venue form — this is "we need to move fast right now," not a considered edit) that collapses the board to 3 columns (2026-09-18+3, down from 4 — `paper` dropped along with the canonical pipeline's own): Registered, Abstract in review, Rebuttal. Not a new status vocabulary — `RUSH_STATUS_ORDER` (`register`, `abstract`, `rebuttal`) is a coherent subsequence of the same `STATUS_ORDER` keys, so the checklist gate and `onChangeStatus` need no special-casing at all: full-order indices already answer "did this cross `GATE_STATUS`" correctly regardless of which order a move happened in, since skipping the omitted statuses doesn't change their relative order. `effectiveStatusOrder(board)` picks the active order; `displayStatus(card, board)` is the only place real work happens — it projects a card whose true `status` isn't a column in the active order onto the last one it's actually passed (e.g. a card at Pitched shows under Registered when Rush mode is on), **without ever rewriting `card.status`** — toggling Rush mode is purely a display change, reversible with zero data loss. A card's status only changes when someone actually moves it, and only ever to a value from whichever order was active for that move — so moving a card while Rush mode is on naturally stays within the 3, and flipping back to the full pipeline later just resumes showing/moving through all 6, nothing was ever silently lost. Rush mode's only remaining divergence from the full pipeline is skipping Pitch — `paper`/`arxiv` used to be its second point of divergence (skipping straight to `rebuttal` a stage early) but that's moot now that the canonical pipeline skips them too. Every place that used to read `card.status`/`STATUS_ORDER` directly to compute Left/Right or the status dropdown now goes through `displayStatus`/`effectiveStatusOrder` instead — grep for both if adding a new one.
   Sub-states that used to be their own column aren't columns any more — they're a badge + colour on the card: Drafted's old Ready-for-review / Changes-Requested / Approved split is `reviewFilterState(card)` (three buckets, for the card's colour and the review-status filter) plus `reviewBadges(card)` (what actually renders — can be more than one at once), rendered via `.rv-*` classes and `badge-rv-*`; Reviews Out's old in-progress/submitted split is derived from whether `rebuttalDocLink` is set. Outcomes (Accepted / Rejected / Withdrawn) aren't phases either — they're `card.outcome`, set from the **Edit fields** modal (`eOutcome`), shown as a `badge-outcome-*` wherever the card currently sits — `shouldShowOutcomeBadge()` suppresses it for an Accepted outcome specifically when the card is already in the Accepted column, since showing it there would just repeat the column name.
   **Nothing here is automatic — 2026-09-11, redesigned same day.** Each reviewer has their own tri-state sign-off: `card.jrReviewState`/`card.srReviewState`, each one of `'in_review' | 'changes_requested' | 'approved'` — none derived from `checklistComplete()`. Ticking every checklist box being complete is still the hard gate on advancing past `GATE_STATUS` (`crossesGate`, unchanged), but it no longer means "Approved" by itself — a reviewer has to explicitly say so, and only **that** reviewer: rendered as three buttons, same line, directly under each reviewer's picker in `.card-reviewers` (`reviewStateButtonsHtml(card, role)`, card face and detail page alike), click-enabled only when `state.currentUser.email` matches `card.reviewers[role]` — everyone else sees the same row, disabled, with a tooltip saying so. This is a client-side-only restriction; the Security Rules' card-update condition is still whole-document (submitter/junior/senior/PI-admin, not field-level — see `firestore.rules`), so it doesn't stop a reviewer from writing the *other* role's field if they bypassed the UI. `onSetReviewState(cardId, role, value)` is the one handler for all six buttons, replacing the short-lived `onToggleChangesRequested`/`onToggleApproval` boolean pair. `reviewFilterState`: `changes_requested` wins if either reviewer is in that state; else `approved` only once **both** are `approved`; else `in_review` (the default, including a partial sign-off). `reviewBadges` shows the fuller picture — a single "Approved" badge once both are, but "JR approved" / "SR approved" individually if only one is. **Auto-advance:** the moment both reach `approved` on a card still in Drafted, `onSetReviewState` moves it straight to Reviewed (`final_draft`) in the same save, still gated by `checklistComplete()` — if the checklist isn't finished yet, the status is left alone rather than skipping that gate; it advances next time a state flips once the checklist catches up, or someone can Advance by hand. **This is also now a hard gate on the manual route** (2026-09-11): `advanceBlockReason()` greys out Advance (and `onChangeStatus()` rejects the status `<select>`/Revert-fallthrough route too) for any move that `crossesGate()` unless `reviewFilterState(card) === 'approved'` — same shape as the pre-existing checklist gate, checked right alongside it, so a card can't leave Drafted for Reviewed by any path until both reviewers have actually signed off, not just ticked every checklist box. The board search bar's second dropdown (`boardReviewFilter` → `state.search.reviewState`, combined via AND with the text query in `matchesSearch`) filters to one of these three buckets — added specifically so "show me everything still needing changes / already approved / still in review" is one click. `normalizeCard()` migrates any card still holding the brief earlier shape (a shared `changesRequested` flag plus independent `jrApproved`/`srApproved` booleans) into the new fields so no reviewer's prior sign-off is lost.
   **A card belongs in a column once that milestone is actually met** — moving it there is an attestation, not a work-in-progress bucket (this is why PI Polish is called **PI Approval**: the column means the PI *has* approved, not that approval is in progress). The title and the hint have opposite tenses on purpose: `STATUS_LABELS` names the checkpoint already met (past tense), `STATUS_HINTS` names what's happening *now*, while the card sits there, or what it's waiting on next (e.g. Registered's hint is "Waiting for pitch", not "Registered") — together they answer both "why is this card here" and "what's actually going on with it." **No confirmation popup on Advance** — there used to be one (`window.confirm()`, a per-status checklist via `STATUS_ADVANCE_CHECKLIST`/`advanceConfirmMessage()`), removed 2026-09-11: native browser confirm dialogs don't reliably appear in every environment, and cards were getting stuck waiting on one that never showed. Moving a card (either direction, through `onChangeStatus`) now just happens — the two *hard* gates (checklist completion before `GATE_STATUS`, reviewers assigned before Draft & Review) are separate, toast-driven checks and are unaffected. Add an entry to both `STATUS_LABELS` and `STATUS_HINTS` whenever a column is added or its meaning changes.
7. **The Internal Review checklist lives entirely in `audit-board.html` now** — `internal-qa-review.html` was a separate, standalone simulated-peer-review page with its own copy of the same 12 items; removed 2026-09-11 since it was redundant with the checklist already on every card (nobody used the standalone page for a review that mattered — the card's checklist is the one that gates Approved). `CHECKLIST_TEMPLATE` (12 entries: `part`, `category`, `label` — 6 format, 6 science, each folding together what used to be several sibling checks) is the only copy left; there's nothing else to keep it in sync with. On a card, each item is `{ id, part, category, label, junior, senior, comments }` — two independent check passes (`REVIEW_ROLES`) plus a per-item feedback thread (see guideline 11). Each card also has `reviewers: { junior, senior }` (each a real person's email — see guideline 8). Assigned **inline on the card face and the detail page** — `reviewerInputHtml()` renders a `<select>`, `onSetReviewer()` saves on change. Deliberately *not* duplicated into the Edit-fields modal — reviewer assignment is meant to be a one-click inline action, not a trip through a form.
   **The detail page's review area is three tabs** — Format, Science, Discussion (`reviewTabsHtml()`, `state.detailTab`, one of `'format'|'science'|'discussion'`, reset to `'format'` in `openCard()`). `checklistTabHtml(card, part)` filters `card.checklist` to one part per tab — same markup as before the split, just one `part` at a time, so `.cl-part` dividers are gone (each panel is already one part). Only the active tab's panel is ever in the DOM (a full string rebuild, not real CSS-hidden panels). Switching tabs is a full `renderCardDetail()`; `onToggleChecklist()`'s partial refresh (gate banner + move controls only, still doesn't touch tab state) is now conditional, not unconditional — see the next paragraph.
   **Ticking a box is restricted to the matching assigned reviewer, and now drives that reviewer's own sign-off automatically (2026-09-11).** `checklistTickAccess(card)` (used by `checklistTabHtml`) disables a role's checkboxes for anyone whose `state.currentUser.email` isn't `card.reviewers[role]` — same client-side-only shape as `reviewStateButtonsHtml`'s tri-state buttons (guideline 6): the Security Rules' card-update condition stays whole-document, not field-level. `onToggleChecklist()` re-checks the same condition itself before writing anything (belt-and-braces against a stray event). Every toggle recomputes each role's checklist completeness and syncs `jrReviewState`/`srReviewState` to match — all of a role's boxes ticked sets that role to `'approved'`; any of them unticked while currently `'approved'` takes it back to `'in_review'` — **except** an explicit `'changes_requested'`, which checklist state never overwrites or clears either way (it's a stronger, separate signal from the reviewer). This can cascade into the same auto-advance-to-Reviewed condition `onSetReviewState` uses (both roles `'approved'`, still in Drafted, `checklistComplete()` — trivially true here since completing the checklist is what triggered this). Because a tick can now change more than the checklist itself (the tri-state buttons, badges, possibly the whole controls row on auto-advance), `onToggleChecklist()` does a full `renderCardDetail()` when the reviewer's own state actually changed or the card auto-advanced, and only falls back to the old gate-banner+move-controls partial refresh on an ordinary tick that crosses no completion boundary.
   **Discussion is a per-card thread, OpenReview-style, one level of replies.** `card.discussion`: array of `{ id, author, authorEmail, timestamp, body, replies }`; a reply (`onPostReply`) is a `{ id, author, authorEmail, timestamp, body }` with **no `replies` field of its own** — that's what caps nesting at one level, there's no UI to reply to a reply. **`author`/`authorEmail` come from `state.currentUser` (2026-09-12), not typed in** — posting requires being signed in (`requireSignedIn()`), same as everything else that needs real identity (`submittedBy`/`reviewers`/`proposedBy`). Older messages posted before this change only have `author` (a free-text name) and no `authorEmail` — anything reading that field (a notification, say) has to handle it being absent. `onPostDiscussion()` appends a top-level message; only the body is required now (no name field to fill in) or the post is rejected with a toast, not silently dropped. Only one reply form is ever open at a time (`state.discussionReplyOpenId`, reset on tab switch and on posting), so the reply input (`#discReplyBody`) can use a fixed id regardless of which thread it belongs to — don't reuse that id for anything else on the page.
   **Every checklist item has its own feedback thread** — same shape and one-level-reply rule as Discussion (including the same 2026-09-12 real-identity change), but scoped to one point (`it.comments`, an array of the same message objects). A checklist row (`.cl-row`) is wrapped in a `.cl-item` with a `.cl-row-foot` toggle beneath it ("Add feedback" / "N comments" / "Hide feedback"); expanding it renders `checklistItemThreadHtml(it)` inline. Only one item's thread is open at a time (`state.checklistCommentOpenId`) and one reply within it (`state.checklistReplyOpenId`); both reset on `openCard()`, tab switch, and (the reply) on posting. Fixed input ids `#clcNewBody` / `#clcReplyBody` — safe for the same reason Discussion's is. Handlers `onPostChecklistComment(cardId, itemId)` / `onPostChecklistReply(cardId, itemId, parentId)` write into `checklist[i].comments`, re-render via `renderCardDetail()` (not the checkbox partial refresh — the thread markup changed), and keep the item's thread open so the reviewer sees it land. `threadCount()` (messages + replies) feeds both the Discussion tab badge and each item's "N comments" label. **Comments never gate anything** — `checklistComplete()` still only reads the `junior`/`senior` booleans; an open concern is a signal to a human, not a hard block. `normalizeCard()` defaults `comments: []` onto any item missing it (and every rebuild path sets it).
8. **Every card has a PI and at least one author — one field, not two.** `card.authors`: array of `{ name, email }` (**changed from plain strings, 2026-09-12** — see below). **No longer required at registration** (changed 2026-09-18+1, per Eduardo, alongside the Overleaf link and the new `abstractText` field below — none of the three are known yet that early): `onAddCard` writes `authors: []`; the registration modal has no author-row UI at all any more. Both become real, gated requirements instead on the transition that actually reaches `abstract` (`advanceBlockReason`'s `toStatus === 'abstract'` checks) — filled in via the Edit-fields modal at Submit the abstract, the same modal and the same `authorRowsHtml()`/`renderAuthorRows()` machinery as before, just with only one caller now (`eAuthorsState`) instead of two. **The PI is the last entry in `authors`**, not a separate field (`cardPi(card)` returns its `name`; use `authors[authors.length-1]` directly for the email too); the last row is tagged "PI" (`.author-pi-tag`) and "+ Add author" inserts *before* it, not after, so it stays last as co-authors are added. Detail page shows `authors.map(a => a.name).join(', ')`. **Not shown on the card face** (removed 2026-09-11 to keep the card shorter) — `cardPi()` still backs the "Authors" search scope's PI variant.
   **Authors resolve to a real person's email now, same as reviewers (2026-09-12) — no more free text.** Each row is a `<select>` over `state.people` (the roster), same picker shape as `reviewerInputHtml`, plus a `+ New author (not in the workspace)…` option that swaps the row to two plain inputs (Name, Email) for a genuine co-author outside the lab's Slack — `.author-select`/`.author-new-name`/`.author-new-email`/`.author-use-roster` (switches a row back to the picker) all wired in `renderAuthorRows()`. A row's `isNew` flag is UI-only (which control to render) and is stripped by `authorsForSave(rows)` before the array is ever saved. `authorRowsIssue(rows)` is the Edit-fields modal's validator: the last row (PI) must be a complete `{name, email}`, and no other non-blank row may be half-filled (only possible in "New author" mode — picking from the roster always sets both fields together). **Why this changed:** free-text authors meant the PI had no reliable email to notify (see the Slack-notifications work, `bold-os#1`, branch `feature/slack-notifications`) — same motivating problem `submittedBy`/`reviewers` already solved for their own fields. A "New author" entry is deliberately *not* added to the shared `people` roster (that collection stays a clean sync of real Slack workspace members — see `docs/FIREBASE.md`) — it's stored only on that card. `normalizeCard()` migrates any card still holding plain-string authors to `{name, email: ''}` (email unrecoverable for old data) — a blank email there means a PI-approval notification on an old, not-yet-re-saved card will silently do nothing until someone re-saves the author list through the picker. The senior-reviewer-defaults-to-PI assignment (guideline 6/7) moved from `onAddCard` to `onSaveEdit` for the same reason — there's no PI to default to until authors actually exist.
   **`submittedBy` and the corresponding-author email are set automatically from the signed-in user at registration, not typed in** (2026-09-11) — registering a paper requires being signed in (`requireSignedIn()`). Neither is in the Edit-fields modal: `submittedBy` because it's what Security Rules authorize card edits against, not free-form metadata to reassign; corresponding-author email stays editable there since it's just paper metadata. **Track and the per-card deadline override no longer exist** (removed 2026-09-11) — a card always inherits its venue's deadline; a different track or deadline is a different venue now, by convention. Edit-fields (`openEditModal()` / `onSaveEdit()`) covers title, authors, Overleaf link, **abstract text** (`abstractText`, free text — may contain LaTeX typed as plain `$inline$`/`$$block$$`, rendered on the detail page via `renderAbstractHtml()`/KaTeX, added 2026-09-18+1), corresponding-author email, compute estimate, alongside the always-there post-submission fields (submission link, rebuttal deadline/doc, review notes, outcome). The only things it deliberately doesn't cover: reviewers (inline, see guideline 7), status (the move buttons / dropdown), and the checklist (the matrix itself).
   **Reviewers (Junior/Senior) resolve to a real person's email, via the real Slack roster — not free text.** `reviewerInputHtml()` renders a `<select>` over `state.people` (the `people` Firestore collection, synced from Slack's `users.list` — see `docs/FIREBASE.md`), `value` = email, so what's actually stored is what Security Rules match against. Authors (and PI, its last entry) stay free text with roster-backed suggestions (`peopleDatalistHtml()`, a `<datalist>`) — deliberately not switched to a closed picker, since a paper's authors can include people outside this Slack workspace.
   **Only the submitter or a PI/admin can actually save a reassignment (2026-09-11)** — `firestore.rules`' `update` rule requires the `reviewers` map be unchanged unless the writer is `submittedBy.email` or `hasFullWrite()`; an assigned reviewer keeps full write access to everything else on their card, just not to who the reviewers are. **Not enforced client-side**: the picker stays enabled for every signed-in lab member (`reviewerInputHtml()` adds only a `title` hint for a non-owner) — PI/admin status isn't readable by the client (`roles/{roleId}` is deny-all, same constraint as Rush mode's toggle in guideline 6), so disabling it for "not the owner" would also block a real PI/admin who has no other way to prove it. An unauthorized save still fails cleanly via the existing permission-denied toast.
9. **The board card (`renderCard()`) is kept short on purpose.** Title (underlined, so it reads as the click target — `data-open-card`), then only what you need to triage at a glance: status/outcome/overdue badges (the `.card-meta-row` div is omitted entirely when there are none), PI line, reviewer inputs (each with its own tri-state review-status row, Drafted only — see guideline 6), checklist progress, and the Revert/Advance buttons. **Not** on the card: track, the Overleaf link, or edit/remove controls — all of those live on the detail page (track in the grid, "Edit fields" and "Remove paper" in `.detail-controls`). The only `.card-footer` left is the orphaned-status rescue `<select>`. When adding something to the card, ask whether it earns its vertical space or belongs on the detail page.
10. **Board search.** A free-text box plus a field select (Everything / Title / PI / Authors) filter the cards shown in `renderColumns()` — `matchesSearch(card)` does the matching, `boardSearchHtml()` renders the bar (with a live match count), `onSearchInput()` re-renders the whole board on every keystroke but saves and restores the input's focus + cursor position first (a plain `renderBoard()` from an `input` handler would otherwise blur the field the user is typing in). A column with cards that all fail the filter shows "No matches"; a column with no cards at all still shows "Nothing here" — that distinction is deliberate. Resets (`state.search`) on `openVenue()`.
11. **Card detail + gates.** Clicking a card title opens a detail view (`state.view === 'card'`) with all fields and the review tabs (guideline 7) — **Junior = teal, Senior = plum** in the checklist tabs (column headers + `accent-color`). Two independent hard gates, both enforced identically on the render side (`advanceBlockReason()` — greys out Advance and sets its tooltip to the reason) and in `onChangeStatus()` (rejects the move with a toast, whichever route triggered it: Advance button, Revert-button fallthrough, or the status `<select>`):
    - **Checklist gate.** `crossesGate()` blocks any *forward* move from before `GATE_STATUS` (`final_draft`) to it or past it until `checklistComplete()` (both passes complete — 12/12 today) — a card can't leave Drafted for Reviewed until both reviewers are done. `normalizeCard()` rebuilds a stored checklist whose length or labels no longer match `CHECKLIST_TEMPLATE` (a card saved under an older, longer shape), carrying a tick forward only for a part a role had *fully* finished; count-derived UI (`checklistCounts()`, the gate banner's `n/total`) reads the length off the card, so it stays correct without hardcoded totals.
    - **Reviewer-approval gate** (2026-09-11). Same `crossesGate()` boundary, checked right alongside the checklist gate — a card can't leave Drafted for Reviewed until `reviewFilterState(card) === 'approved'` (both `jrReviewState` and `srReviewState` are `'approved'`, see guideline 6). A separate check from the checklist gate, enforced independently — but as of the same day, `onToggleChecklist()`'s auto-sync (guideline 7) means finishing both roles' checklists usually satisfies both gates in one action, unless a reviewer has explicitly flagged `'changes_requested'` (which checklist completion never overrides), so the two can still diverge.
    - **Reviewers-assigned gate.** A card can't Advance into Drafted (from Pitched, normally) unless `reviewersAssigned(card)` — both `reviewers.junior` and `reviewers.senior` set. Only blocks the forward direction; reverting back into Drafted (e.g. from Reviewed) is never blocked by it.
    Add a new gate by extending `advanceBlockReason()` (render side) and adding the matching `isAdvance`-guarded check in `onChangeStatus()` (enforcement side) — keep both in sync, or the button and the toast will disagree.
    `normalizeCard()` migrates older stored cards (status keys — see guideline 6 — plus single-`checked` / `author`-`auditor` / `author`-`junior`-`senior` checklist shapes → `junior`/`senior`, old `auditor` → `senior`, `author` dropped; a legacy `assignedTo` → `reviewers.junior`; `jrReviewState`/`srReviewState`/`outcome`/`authors` default in for cards that predate them, the former from any still-older `changesRequested`/`jrApproved`/`srApproved` shape — see guideline 6; a still-older separate `pi` field is folded into `authors` as the last entry, then dropped).
12. **Venue schedule + .ics.** A venue carries `deadline` (paper), an optional explicit `pitchDay`, and its own dates (`abstractDeadline`, `reviewsPublicDate`, `rebuttalDeadline`, `notificationDate`, `cameraReadyDeadline`). `internalSchedule(v)` returns one chronological list: derived milestones (register −8 wk, pitch, first/final draft, PI approval) then every venue date present. `venueScheduleHtml` renders it as a horizontal timeline (`vs-rail`, one dot per milestone, even-spaced; `short` label + `formatDateShort` date under each); `buildIcs` / `downloadIcs` export it. Keep milestone `key`s stable — they're the `.ics` UIDs.
13. **Venue proposals** (2026-09-11, branch `feature/venue-proposals`, not yet merged). Any signed-in lab member can propose a new venue — the exact same "+ New venue" button and form a PI/admin uses (`venueFieldsHtml`/`readVenueFields`, unchanged) — but `onCreateBoard()` always tries a direct create (`status:'approved'`) first and only falls back to a self-attributed pending one (`status:'pending'`, `proposedBy:{name,email}`) on a permission-denied specifically; there's no client-side "am I admin" precheck to branch on instead (see below). A pending proposal is visible only to its proposer and to PI/admin, via a Security Rules change on `boards/{boardId}` — see `firestore.rules` and `docs/FIREBASE.md`'s "Venue proposals" section for the read-rule shape and why list queries needed restructuring (`fetchVisibleBoards()`, used by both `loadBoardsIndex()` and `saveBoardsIndex()`) rather than the old plain `boards.get()`. `renderVenuesList()` splits `state.boards` into three sections: the normal approved/openable list, "Your proposals awaiting approval" (own pending), and — only when `state.canApproveVenues` (learned from whether the unfiltered pending query itself succeeded, the only way the client can tell it's PI/admin, since roles stay unreadable) — "Pending your approval". **Every row, pending or approved, opens the normal venue page** (2026-09-11, revised same day) — a pending venue's page shows a "Pending approval" badge next to its title, a `proposerLabel()`-rendered "Proposed by Name (email)" line (always both — a name alone isn't enough to tell two proposals apart, same helper used everywhere a proposer is shown), an empty board, and no "+ Register paper" button at all (see below). **Approve/Reject appear in two places** (revised again same day, per Eduardo: reviewing shouldn't require a click-in first) — inline in the "Pending your approval" list row *and* in the venue detail page's header, next to Edit venue — both wired to the same `onApproveVenue(id)`/`onRejectVenue(id)`, shown only when `state.canApproveVenues`. `onApproveVenue` flips `status` to `'approved'` (same `saveBoardsIndex` write path and `hasFullWrite()` gate as any other venue edit); `onRejectVenue` deletes the proposal outright (same underlying write as `onDeleteBoard()`, since there's nothing worth keeping — no cards can exist on an unapproved venue, no rejection-reason field in the schema) but has its own confirm/toast wording, and stays visually separate from "Delete this venue" (which now only shows once a venue is actually approved). Approve/Reject are same-size, same-weight buttons (`.btn-approve`/`.btn-reject`, green/red fills) — a deliberately neutral, symmetric either-way pairing, not a primary/plain one that would visually suggest which answer is "correct." Since a pending "Pending your approval" row now has other buttons in it, the row itself can't be a `<button>` any more (invalid HTML) — it's a `<div class="venue-row venue-row--pending">` with its own nested clickable name (`.venue-name-btn`) and Approve/Reject as siblings, not children, of that button. A pending venue's board can't accept a registered paper — "+ Register paper" isn't rendered at all on it (2026-09-11, revised from an earlier disabled-with-tooltip version — Eduardo: it shouldn't be there, not just unusable), `openModal()` still carries the same check as a defense-in-depth backstop for anyone who'd somehow trigger it another way. **"+ New venue" itself reads "+ Propose venue" for anyone who isn't a confirmed PI/admin** (`updateNewVenueButtonState()`, driven by the same `state.canApproveVenues`, called from `renderAll()` so it stays current once boards load) — the modal's title/submit-label (`openNewVenueModal()`) follow the same split ("Propose new venue"/"Propose" vs. "New venue"/"Create"), same form and `onCreateBoard()` either way. **Before this can deploy**: every board created before this feature has no `status` field — a rule's `.get('status','approved')` covers a single-document read fine, but the new `where('status','==','approved')` query can't match a field that isn't there, so existing venues need a one-time `status:'approved'` backfill (under the *old* rules) before the new rules + query-based loading go live together — see `docs/FIREBASE.md` for the exact sequencing.
14. **Slack notifications** (`bold-os#1`, branch `feature/slack-notifications`, built and deployed 2026-09-12 — live in production, verified with real Slack DMs; the branch itself isn't merged to `main` yet, but that only affects `docs/`/`firebase.json`/`.gitignore` history, not whether the functions are live — Cloud Functions deploys aren't tied to a git branch the way GitHub Pages' branch-deploy is). `functions/index.js` — the project's only server-side code, a real Node/`npm` project (`functions/package.json`), not part of the plain-HTML client at all. Two Firestore triggers plus one scheduled trigger (`notifyReviewsOut`, see below), all in `europe-west2`: `onVenueProposed` (a new `boards/{boardId}` with `status:'pending'` → DMs every PI/admin) and `onCardWritten` (one trigger covering four independent checks against the same before/after diff — reviewer sign-off → DMs the submitter; new reviewer assignment → DMs that person; any status change → DMs the submitter; reaching `pi_polish` → *also* DMs the PI specifically; a new Discussion/checklist comment → DMs submitter + both reviewers, excluding the poster). **Structure mirrors the client's own pattern**: `cardEventsToNotify(before, after, title, boardId, cardId)` is pure decision logic (no Firestore, no Slack, no `await`) returning `{ emails, headline, url, excludeEmail? }` entries; the actual trigger is a thin wrapper that resolves each to Slack ids (via the `people` roster, not a live `users.lookupByEmail` call) and sends. This split is what let the whole decision surface get verified with 36 standalone unit-test cases (grown over three rounds of live-message feedback, see docs/FIREBASE.md) before ever touching a real Slack workspace — same evidence-first approach used throughout this session. Depends on the same-day author/comment identity fixes (guideline 8) — a PI or comment poster with no email on file just produces fewer notifications, never an error. Uses the Admin SDK (`admin.firestore()`), which bypasses Security Rules entirely (legitimate server-side privileged access, not a workaround) — no `firestore.rules` changes needed for this.
    **`notifyReviewsOut` (2026-09-18+3, per Eduardo) — the file's first *scheduled* trigger**, not reacting to a write or an HTTP request like everything above: `onSchedule({ schedule: 'every 60 minutes' }, ...)` from `firebase-functions/v2/scheduler`, same `europe-west2`/`SLACK_BOT_TOKEN` setup as the rest. Goes with the `paper`/`arxiv` → `rebuttal` collapse (guideline 6) — a card lands in `rebuttal` the moment "Submit paper" is clicked, showing a "Waiting for reviews" badge (`rebuttalBadgeHtml` in `audit-board.html`) until this function flips it to "In Rebuttal" and DMs the submitter, the instant the venue's own `reviewsPublicDate` passes. Same pure-decision-plus-thin-wrapper split as `cardEventsToNotify`: `reviewsOutCandidates(boardsWithCards, todayIso)` is pure (no Firestore, no Slack), the scheduled function does two query passes (Firestore can't join a board-level date filter against a cards subcollection in one go) — boards whose `reviewsPublicDate` has passed, then each one's `rebuttal`-status cards — and sets `card.reviewsOutNotifiedAt` (checked falsy everywhere, not `== null`, so an older card that predates the field still qualifies) before sending, so a re-run never double-DMs. Reuses `dmByEmail`/`linkedTitle`/`cardUrl` unchanged.

**Real deep links, added same day.** Every message used to just paste the flat `audit-board.html` URL as plain text — no way to land on the actual paper/venue. Fixed: `audit-board.html` now has real, bookmarkable URLs (`stateUrl(view, boardId, cardId, baseUrl)` builds a hash — `#board=<id>` or `#board=<id>&card=<id>`, since this is a static site with no server-side routing; `pushNavState()` now passes this as `history.pushState`'s third argument, which it never did before). `parseDeepLinkHash(hash)` is the reverse — captured once at script load into `pendingDeepLink`, applied by `applyPendingDeepLink()` the first time `loadInitialData()` has boards to check it against, and never retried after that (a later reload in the same page load is a normal reload, not a fresh deep link). A venue/card that doesn't exist and one that exists-but-isn't-visible-to-this-viewer (see `fetchVisibleBoards()`, guideline 13) get the identical toast — deliberately not distinguishing the two. `functions/index.js` mirrors this exactly (`venueUrl`/`cardUrl`, same hash shape, kept in sync by hand like `STATUS_LABEL` already was).

**Message design went through several rounds of live feedback the same day** — current state: `linkedTitle(text, url)` (Slack mrkdwn's `<url|*text*>`) makes the paper/venue name the message's one clickable element; an earlier version also sent Slack Block Kit with a separate button, removed once the linked title made it redundant (plain `text` renders the bold link fine on its own — no `blocks` needed). Emoji are grouped by meaning, not one-per-event-type: 🔔 = needs your decision (venue proposal, PI-approval), 🔍 = you've been handed a reviewing task, ✅/❌/↩️ = a reviewer's own sign-off outcome (one per role that changed, leading the message — a mixed outcome in one write shows both glyphs together), ➡️/💬 unchanged. **Comment routing** was revised from a flat "DM submitter + both reviewers, excluding the poster" once real testing showed that over-notified: a new top-level Discussion message still goes to every stakeholder except the poster, but a **reply** goes only to people already in that specific thread (the original poster + prior repliers); a **checklist-item comment** treats the submitter and each reviewer as a 1:1 conversation — the submitter posting notifies both reviewers (one shared thread can't tell which one it's for), but a reviewer posting notifies only the submitter, not the other reviewer. To deploy after a change here: add `chat:write`/`im:write` Slack Bot Token Scopes and reinstall the app, `firebase functions:secrets:set SLACK_BOT_TOKEN`, then `firebase deploy --only functions` — see `docs/FIREBASE.md` for the full writeup.
15. **Slack App Home dashboard + reviewer assignment** (`bold-os#3`, built 2026-09-12, deployed + debugged + verified live 2026-09-13/14 — LIVE). Started as two separate ideas (a reviewer-assignment slash-command/button; a per-person "what's mine" dashboard in Slack's App Home) and was combined into one, since both need the same App Home + Interactivity Slack config and the reviewer picker is naturally one interactive element inside the dashboard rather than a separate flow. One HTTP-triggered function, `exports.slackEvents` (`onRequest`, `invoker: 'public'`, unlike the two Firestore-triggered notification functions above) — handles Slack's Events API (the `url_verification` handshake, then `app_home_opened`), Interactivity (`block_actions`), and Select Menus (`block_suggestion`) all at the same URL, since the request-signature check is identical across all three. Every request is verified against Slack's signing scheme first (`verifySlackSignatureRaw` — HMAC-SHA256 over `v0:{timestamp}:{raw body}`, `SLACK_SIGNING_SECRET`, 5-minute replay window) before anything in the body is trusted. `app_home_opened` resolves the Slack user id to an email (`emailForSlackId`, the reverse of `slackIdForEmail`), runs four `db.collectionGroup('cards')` queries (submitted / reviewing-junior / reviewing-senior / authoring, the last via a denormalized `authorEmails: string[]` field — Firestore's `array-contains` can't match a partial object inside `authors: {name,email}[]` directly), caps each to the 10 most-recently-updated, and `views.publish`es a four-section Block Kit Home view. Each Registered card carries an inline reviewer picker — **`external_select`, not `static_select`** (fixed 2026-09-13, a real bug found live-testing: Slack caps any select's option list at 100, and the 274-person roster silently truncated after the 100th name — `external_select` + `handleBlockSuggestion`/`filterPeopleOptions` instead live-search the whole roster as the viewer types, no fixed list). Picking a name re-checks the exact same permission `firestore.rules` already enforces for reassigning reviewers (`canAssignReviewer` — submitter or PI/admin only, hand-kept in sync with the rule since this write goes through the Admin SDK and bypasses Security Rules entirely) before writing `reviewers.{role}` + `updatedAt`, same shape as `onSetReviewer`. `audit-board.html`'s `loadCurrentBoardCards()` also switched from a one-time `.get()` to a live `onSnapshot` listener (2026-09-14) so a reviewer assigned via Slack shows up on an already-open board without a manual reload — torn down on leaving the board or signing out (`stopWatchingCards()`). 48 standalone unit-test cases pass, and the whole flow (dashboard render, live search past the old 100-cap, reviewer-assignment write-back, DM notification firing, web-app live update) is confirmed working against the real Slack workspace and production Firestore. Several real production bugs were found and fixed getting here — Socket Mode silently diverting all HTTP delivery, a fire-and-forget async handler not reliably completing on Cloud Functions v2, a missed `firestore.indexes.json` deploy, and two pre-existing cards with pre-migration plain-string authors needing a hand-confirmed backfill — see docs/FIREBASE.md's "Real bugs found live-testing" for the full account; worth reading before touching this function again.
