# AGENTS.md

Context for anyone — agent or human — editing this project.

## What this is

An internal tool suite for BOLD Lab's paper-submission process, built as an **implementation of BOLDiquette § ML Conference Cycle** — and, ahead of BOLDiquette, of the real pre-submission runway the lab runs (register 8 wk out · Pitch Day 6 wk · first draft + Internal Review 4 wk · final draft 2 wk · PI approval 1 wk · submit). Three self-contained HTML pages (plus an `index.html` redirect stub) and tracking docs. No build step, no framework — a Firebase backend (Firestore/Auth/Storage) as of 2026-09-11, everything else still plain HTML/CSS/JS.

**Layout, reorganized 2026-09-11:** the served pages and Firebase config stay at repo root (GitHub Pages serves from root; `firebase` CLI expects its config there by default). Contributor-facing docs live in `docs/`; the shippable guide bundle lives in `dist/`.

## Running it

```
python3 -m http.server 8137
```

Then open `index.html` (redirects to `how-to-submit-a-paper.html`), or any of `how-to-submit-a-paper.html`, `audit-board.html`, `diff.html` directly. `how-to-submit-a-paper.html`/`diff.html`/`index.html` also work opened as plain `file://` pages. `audit-board.html` needs to be served (not opened as a bare file): it talks to Firebase (Firestore/Auth/Storage), and Sign-in-with-Slack's popup flow needs a real `http(s)` origin.

**`audit-board.html` talks to real production Firestore by default** (`FIRESTORE_USE_EMULATOR = false`, `AUTH_USE_EMULATOR = false`). For local dev against a disposable local Firestore instead (e.g. testing something that writes data you don't want landing for real): run the Firestore emulator (`firebase emulators:start --only firestore`, needs a JVM — see `docs/FIREBASE.md` for the portable-JDK workaround used when Homebrew's `openjdk` won't install), flip `FIRESTORE_USE_EMULATOR = true` locally, and don't commit that. `AUTH_USE_EMULATOR` can stay `false` even then — the emulator accepts real Firebase Auth ID tokens fine, and the local Auth emulator doesn't have the `oidc.slack` provider anyway. **This flag shipped wrong once already** (committed `true`, silently broke the live site for anyone without a local emulator running, caught 2026-09-11 when a real second user hit it) — double-check both are `false` before committing/pushing. There's now also a loud, hard-to-miss red banner (`#emulatorWarning`/`.emulator-warning`) that shows across the whole page whenever `FIRESTORE_USE_EMULATOR` is `true` — a safety net so a repeat of that mistake would be immediately visible on the live page, not just catchable by re-reading the source. Toggled once, right next to the flag itself, not tied to any render function.

## Deployment

Every push to `main` deploys automatically — GitHub Pages' own "Deploy from a branch" source (`main`, `/`), no workflow file, nothing to run by hand. (Briefly switched to a GitHub Actions-based deploy on 2026-09-11, reverted the same day back to the plain branch deploy.) Live at <https://bold-lab-ai.github.io/ml-conference-cycle/how-to-submit-a-paper.html>.

**New work happens on a branch, not directly on `main`, as of 2026-09-11.** The site is live and in real use now — every feature up to and including this point in the day shipped straight to `main` (each push deploys immediately, and several changes this session also deployed live Firestore Security Rules alongside the client code). From here on: build and commit on a feature branch, get it reviewed/tried, then merge to `main` — merging is what deploys, since there's no separate staging environment. A **Security Rules** change on a branch is not itself live until someone explicitly deploys it (`firebase deploy --only firestore`) — deploying rules and merging the matching client code to `main` should happen together, in the sequence the rules change's own docs/FIREBASE.md section calls for, not the rules going live first on their own.

## Constraints

- **No Claude / Claude-Artifacts dependency.** Never depended on Claude's artifact-storage API; the Internal Review Board persisted to per-browser `localStorage` at first, then moved to a real shared Firebase backend (Firestore/Auth/Storage, `bold-d7ff2`) on 2026-09-11 — see `docs/FIREBASE.md`. `loadBoardsIndex` / `saveBoardsIndex` / `loadBoard` / `saveBoard` / `deleteBoardData` is still the seam every caller in the file goes through; only what's behind those five functions changed.
- **External resources: Google Fonts, plus the Firebase SDK, on `audit-board.html` only.** Everything else — CSS, JS — is inline. No bundler, ever. The Firebase exception (approved 2026-09-11, see `docs/FIREBASE.md`) is the **compat build** from `gstatic.com`, pinned to an exact version, e.g. `https://www.gstatic.com/firebasejs/10.14.1/firebase-app-compat.js` — deliberately the compat (non-module) build so it loads as an ordinary blocking `<script src>`, matching the file's existing classic-script style, rather than the modular/ES-import build (which would need `type="module"` and its deferred-execution timing doesn't mix cleanly with the page's plain IIFE). Bump the version deliberately, not silently.
- **Every page keeps a no-JS fallback.** The guide stacks all phases; the review page stacks both parts. Don't break these.
- **Design tokens match bold-lab.ai** (the pages are meant to live at `https://bold-lab.ai/`). Each `<style>` opens with the same `:root`: `--ink:#09111f`, `--ink-soft`, `--muted:#667085`, `--paper:#fbfaf6` (page), `--surface:#fff` (cards/columns/inputs/modals), `--wash:#eef2f4`, `--line:#d8dee6`; accents `--blue` (links + primary buttons), `--teal` (Format + eyebrows), `--plum` (Science), `--amber` (attention); `--focus:#c87912` (amber focus ring); `--radius:8px`. Headings are Inter `font-weight:760`, `letter-spacing:0`. Eyebrows: uppercase, **no** letter-spacing, teal. No serif, no middot-joined meta strings, no trailing `→` on non-directional links. `audit-board.html`'s `:root` also re-defines the legacy names its inline JS styles reference (`--accent`, `--accent-dim`, `--neutral-bg/-text`, `--warn-*`, `--success-*`, `--danger-*`) — keep those.
- **Names are unified as "Internal Review" / "Internal Review Board" / "reviewer".** `audit-board.html`'s filename, CSS classes (`cl-*`, `card-*`), and JS identifiers keep their old spellings on purpose — renaming them is churn with migration risk and no user benefit.

## Editing guidelines

1. **It implements BOLDiquette.** Any place the process differs, record it in `docs/DIFF.md` with a proposed BOLDiquette change. **Never** put "this differs from BOLDiquette" commentary in the pages themselves. **Editing `docs/DIFF.md` means also editing `diff.html`** (the rendered page the three `.page-source` links point at) — there's no build step, so keep the two in sync by hand: same items, same order, same wording.
2. Each page carries **one** BOLDiquette citation (the guide's is a `.page-source` line under the title; the review page and board use `.page-source` too), ending `&middot; current differences in <a href="diff.html">DIFF.md</a>`. No per-phase source lines.
3. **Copy is terse.** Descriptions (`meta`/OG + hero ledes) are one or two sentences. No throat-clearing, no narrating process or rationale, no knowing-aside / internal-monologue lines. Only what the reader needs to act.
4. Keep an element only if removing it would make the page worse.
5. **Changing phases** (`how-to-submit-a-paper.html`): update the TOC `href`s and labels, each `<section>`'s `id` and `.phase-num`, the `.timeline` rail (`<li>` per phase, `--n` on the `<ol>`, `is-pivot`/`is-after` classes), the pager's static `Phase 1 of N`, and any cross-references (`(Phase 6)`). The JS derives the pager from the TOC hrefs; timeline links are wired via `links.concat(tl)` and synced in `showPhase`.
6. **Board columns = the guide's 9 phases, one for one — but worded differently on purpose.** `STATUS_ORDER` is the same 9 phases, same order, as the `.timeline` in `how-to-submit-a-paper.html` (Register, Pitch Day, First Draft & Internal Review, Final Draft, PI Approval, Submit, arXiv & Publicity, Rebuttal, Pre-Conference) — adding, removing, or reordering a phase in one without the other is a bug. `STATUS_LABELS`, though, is deliberately **past tense** — Registered, Pitched, Drafted, Reviewed, PI Approved, Submitted, Posted, Reviews Out, Accepted — because a column names the checkpoint already met to be sitting in it (see guideline 11's gates), where the guide's headings are instructional ("Pitch Day", "Submit") telling you what to go do. Same phase, two label styles for two different jobs; don't try to make them match verbatim. Change `STATUS_LABELS` / `STATUS_HINTS` (the "move a card here when…" line under each column title) text freely. Changing a `STATUS_ORDER` **key** rewrites stored data — any card already at that status is orphaned to the "Other" column. If you must, add the old→new mapping to `STATUS_MIGRATIONS` so existing cards migrate on load (and, if the old status carried information a rename alone would lose, set the matching field in `normalizeCard()` too — see `STATUS_OUTCOME_MIGRATIONS` and the `changes_requested` case for the pattern). `.columns`' `min-width` (240px × columns + 1px × gaps + 2px border) is computed in `renderColumns()` from however many columns are actually rendering, not hardcoded — Rush mode (below) is exactly why that stopped being a fixed number.
   **Rush mode, added 2026-09-11 — the one deliberate exception to "columns = the guide's 9 phases."** A per-venue toggle (`board.rushMode`, a one-click button in the venue header, not a field in the Edit-venue form — this is "we need to move fast right now," not a considered edit) that collapses the board to 4 columns: Registered, Drafted, Reviewed, Submitted. Not a new status vocabulary — `RUSH_STATUS_ORDER` is a coherent subsequence of the same `STATUS_ORDER` keys (`register`, `draft_review`, `final_draft`, `submit`), so the checklist gate and `onChangeStatus` need no special-casing at all: full-order indices already answer "did this cross `GATE_STATUS`" correctly regardless of which order a move happened in, since skipping the omitted statuses doesn't change their relative order. `effectiveStatusOrder(board)` picks the active order; `displayStatus(card, board)` is the only place real work happens — it projects a card whose true `status` isn't a column in the active order onto the last one it's actually passed (e.g. a card at Pitched shows under Registered when Rush mode is on), **without ever rewriting `card.status`** — toggling Rush mode is purely a display change, reversible with zero data loss. A card's status only changes when someone actually moves it, and only ever to a value from whichever order was active for that move — so moving a card while Rush mode is on naturally stays within the 4, and flipping back to the full pipeline later just resumes showing/moving through all 9, nothing was ever silently lost. Every place that used to read `card.status`/`STATUS_ORDER` directly to compute Left/Right or the status dropdown now goes through `displayStatus`/`effectiveStatusOrder` instead — grep for both if adding a new one.
   Sub-states that used to be their own column aren't columns any more — they're a badge + colour on the card: Drafted's old Ready-for-review / Changes-Requested / Approved split is `reviewFilterState(card)` (three buckets, for the card's colour and the review-status filter) plus `reviewBadges(card)` (what actually renders — can be more than one at once), rendered via `.rv-*` classes and `badge-rv-*`; Reviews Out's old in-progress/submitted split is derived from whether `rebuttalDocLink` is set. Outcomes (Accepted / Rejected / Withdrawn) aren't phases either — they're `card.outcome`, set from the **Edit fields** modal (`eOutcome`), shown as a `badge-outcome-*` wherever the card currently sits — `shouldShowOutcomeBadge()` suppresses it for an Accepted outcome specifically when the card is already in the Accepted column, since showing it there would just repeat the column name.
   **Nothing here is automatic — 2026-09-11, redesigned same day.** Each reviewer has their own tri-state sign-off: `card.jrReviewState`/`card.srReviewState`, each one of `'in_review' | 'changes_requested' | 'approved'` — none derived from `checklistComplete()`. Ticking every checklist box being complete is still the hard gate on advancing past `GATE_STATUS` (`crossesGate`, unchanged), but it no longer means "Approved" by itself — a reviewer has to explicitly say so, and only **that** reviewer: rendered as three buttons, same line, directly under each reviewer's picker in `.card-reviewers` (`reviewStateButtonsHtml(card, role)`, card face and detail page alike), click-enabled only when `state.currentUser.email` matches `card.reviewers[role]` — everyone else sees the same row, disabled, with a tooltip saying so. This is a client-side-only restriction; the Security Rules' card-update condition is still whole-document (submitter/junior/senior/PI-admin, not field-level — see `firestore.rules`), so it doesn't stop a reviewer from writing the *other* role's field if they bypassed the UI. `onSetReviewState(cardId, role, value)` is the one handler for all six buttons, replacing the short-lived `onToggleChangesRequested`/`onToggleApproval` boolean pair. `reviewFilterState`: `changes_requested` wins if either reviewer is in that state; else `approved` only once **both** are `approved`; else `in_review` (the default, including a partial sign-off). `reviewBadges` shows the fuller picture — a single "Approved" badge once both are, but "JR approved" / "SR approved" individually if only one is. **Auto-advance:** the moment both reach `approved` on a card still in Drafted, `onSetReviewState` moves it straight to Reviewed (`final_draft`) in the same save, still gated by `checklistComplete()` — if the checklist isn't finished yet, the status is left alone rather than skipping that gate; it advances next time a state flips once the checklist catches up, or someone can Advance by hand. **This is also now a hard gate on the manual route** (2026-09-11): `advanceBlockReason()` greys out Advance (and `onChangeStatus()` rejects the status `<select>`/Revert-fallthrough route too) for any move that `crossesGate()` unless `reviewFilterState(card) === 'approved'` — same shape as the pre-existing checklist gate, checked right alongside it, so a card can't leave Drafted for Reviewed by any path until both reviewers have actually signed off, not just ticked every checklist box. The board search bar's second dropdown (`boardReviewFilter` → `state.search.reviewState`, combined via AND with the text query in `matchesSearch`) filters to one of these three buckets — added specifically so "show me everything still needing changes / already approved / still in review" is one click. `normalizeCard()` migrates any card still holding the brief earlier shape (a shared `changesRequested` flag plus independent `jrApproved`/`srApproved` booleans) into the new fields so no reviewer's prior sign-off is lost.
   **A card belongs in a column once that milestone is actually met** — moving it there is an attestation, not a work-in-progress bucket (this is why PI Polish is called **PI Approval**: the column means the PI *has* approved, not that approval is in progress). The title and the hint have opposite tenses on purpose: `STATUS_LABELS` names the checkpoint already met (past tense), `STATUS_HINTS` names what's happening *now*, while the card sits there, or what it's waiting on next (e.g. Registered's hint is "Waiting for pitch", not "Registered") — together they answer both "why is this card here" and "what's actually going on with it." **No confirmation popup on Advance** — there used to be one (`window.confirm()`, a per-status checklist via `STATUS_ADVANCE_CHECKLIST`/`advanceConfirmMessage()`), removed 2026-09-11: native browser confirm dialogs don't reliably appear in every environment, and cards were getting stuck waiting on one that never showed. Moving a card (either direction, through `onChangeStatus`) now just happens — the two *hard* gates (checklist completion before `GATE_STATUS`, reviewers assigned before Draft & Review) are separate, toast-driven checks and are unaffected. Add an entry to both `STATUS_LABELS` and `STATUS_HINTS` whenever a column is added or its meaning changes.
7. **The Internal Review checklist lives entirely in `audit-board.html` now** — `internal-qa-review.html` was a separate, standalone simulated-peer-review page with its own copy of the same 12 items; removed 2026-09-11 since it was redundant with the checklist already on every card (nobody used the standalone page for a review that mattered — the card's checklist is the one that gates Approved). `CHECKLIST_TEMPLATE` (12 entries: `part`, `category`, `label` — 6 format, 6 science, each folding together what used to be several sibling checks) is the only copy left; there's nothing else to keep it in sync with. On a card, each item is `{ id, part, category, label, junior, senior, comments }` — two independent check passes (`REVIEW_ROLES`) plus a per-item feedback thread (see guideline 11). Each card also has `reviewers: { junior, senior }` (each a real person's email — see guideline 8). Assigned **inline on the card face and the detail page** — `reviewerInputHtml()` renders a `<select>`, `onSetReviewer()` saves on change. Deliberately *not* duplicated into the Edit-fields modal — reviewer assignment is meant to be a one-click inline action, not a trip through a form.
   **The detail page's review area is three tabs** — Format, Science, Discussion (`reviewTabsHtml()`, `state.detailTab`, one of `'format'|'science'|'discussion'`, reset to `'format'` in `openCard()`). `checklistTabHtml(card, part)` filters `card.checklist` to one part per tab — same markup as before the split, just one `part` at a time, so `.cl-part` dividers are gone (each panel is already one part). Only the active tab's panel is ever in the DOM (a full string rebuild, not real CSS-hidden panels). Switching tabs is a full `renderCardDetail()`; `onToggleChecklist()`'s partial refresh (gate banner + move controls only, still doesn't touch tab state) is now conditional, not unconditional — see the next paragraph.
   **Ticking a box is restricted to the matching assigned reviewer, and now drives that reviewer's own sign-off automatically (2026-09-11).** `checklistTickAccess(card)` (used by `checklistTabHtml`) disables a role's checkboxes for anyone whose `state.currentUser.email` isn't `card.reviewers[role]` — same client-side-only shape as `reviewStateButtonsHtml`'s tri-state buttons (guideline 6): the Security Rules' card-update condition stays whole-document, not field-level. `onToggleChecklist()` re-checks the same condition itself before writing anything (belt-and-braces against a stray event). Every toggle recomputes each role's checklist completeness and syncs `jrReviewState`/`srReviewState` to match — all of a role's boxes ticked sets that role to `'approved'`; any of them unticked while currently `'approved'` takes it back to `'in_review'` — **except** an explicit `'changes_requested'`, which checklist state never overwrites or clears either way (it's a stronger, separate signal from the reviewer). This can cascade into the same auto-advance-to-Reviewed condition `onSetReviewState` uses (both roles `'approved'`, still in Drafted, `checklistComplete()` — trivially true here since completing the checklist is what triggered this). Because a tick can now change more than the checklist itself (the tri-state buttons, badges, possibly the whole controls row on auto-advance), `onToggleChecklist()` does a full `renderCardDetail()` when the reviewer's own state actually changed or the card auto-advanced, and only falls back to the old gate-banner+move-controls partial refresh on an ordinary tick that crosses no completion boundary.
   **Discussion is a per-card thread, OpenReview-style, one level of replies.** `card.discussion`: array of `{ id, author, timestamp, body, replies }`; a reply (`onPostReply`) is a `{ id, author, timestamp, body }` with **no `replies` field of its own** — that's what caps nesting at one level, there's no UI to reply to a reply. `author` is free text (same shared `peopleNames` datalist as PI/authors — see guideline 8; reviewers moved to a real roster `<select>`, this hasn't yet). `onPostDiscussion()` appends a top-level message; both require a non-empty name and body or the post is rejected with a toast, not silently dropped. Only one reply form is ever open at a time (`state.discussionReplyOpenId`, reset on tab switch and on posting), so the reply inputs (`#discReplyAuthor`/`#discReplyBody`) can use fixed ids regardless of which thread they belong to — don't reuse those ids for anything else on the page.
   **Every checklist item has its own feedback thread** — same shape and one-level-reply rule as Discussion, but scoped to one point (`it.comments`, an array of the same message objects). A checklist row (`.cl-row`) is wrapped in a `.cl-item` with a `.cl-row-foot` toggle beneath it ("Add feedback" / "N comments" / "Hide feedback"); expanding it renders `checklistItemThreadHtml(it)` inline. Only one item's thread is open at a time (`state.checklistCommentOpenId`) and one reply within it (`state.checklistReplyOpenId`); both reset on `openCard()`, tab switch, and (the reply) on posting. Fixed input ids `#clcNew*` / `#clcReply*` — safe for the same reason Discussion's are. Handlers `onPostChecklistComment(cardId, itemId)` / `onPostChecklistReply(cardId, itemId, parentId)` write into `checklist[i].comments`, re-render via `renderCardDetail()` (not the checkbox partial refresh — the thread markup changed), and keep the item's thread open so the reviewer sees it land. `threadCount()` (messages + replies) feeds both the Discussion tab badge and each item's "N comments" label. **Comments never gate anything** — `checklistComplete()` still only reads the `junior`/`senior` booleans; an open concern is a signal to a human, not a hard block. `normalizeCard()` defaults `comments: []` onto any item missing it (and every rebuild path sets it).
8. **Every card has a PI and at least one author — one field, not two.** `card.authors` (string array), required at registration and in the Edit-fields modal alike. **The PI is the last entry in `authors`**, not a separate field (`cardPi(card)` returns it). It's a dynamic list of rows — `authorRowsHtml()` / `renderAuthorRows(wrapId, authorsArr, onEnter)`, shared by both modals via their own backing array (`pAuthorsState` for registration, `eAuthorsState` for Edit fields) and wrap/button ids (add/remove without losing what's already typed in other rows); the last row is tagged "PI" (`.author-pi-tag`) and "+ Add author" inserts *before* it, not after, so it stays last as co-authors are added. `authors.join(', ')` shown on the detail page. **Not shown on the card face** (removed 2026-09-11 to keep the card shorter) — `cardPi()` still backs the "Authors" search scope's PI variant.
   **`submittedBy` and the corresponding-author email are set automatically from the signed-in user at registration, not typed in** (2026-09-11) — registering a paper requires being signed in (`requireSignedIn()`). Neither is in the Edit-fields modal: `submittedBy` because it's what Security Rules authorize card edits against, not free-form metadata to reassign; corresponding-author email stays editable there since it's just paper metadata. **Track and the per-card deadline override no longer exist** (removed 2026-09-11) — a card always inherits its venue's deadline; a different track or deadline is a different venue now, by convention. Edit-fields (`openEditModal()` / `onSaveEdit()`) covers title, authors, Overleaf link, corresponding-author email, compute estimate, alongside the always-there post-submission fields (submission link, rebuttal deadline/doc, review notes, outcome). The only things it deliberately doesn't cover: reviewers (inline, see guideline 7), status (the move buttons / dropdown), and the checklist (the matrix itself).
   **Reviewers (Junior/Senior) resolve to a real person's email, via the real Slack roster — not free text.** `reviewerInputHtml()` renders a `<select>` over `state.people` (the `people` Firestore collection, synced from Slack's `users.list` — see `docs/FIREBASE.md`), `value` = email, so what's actually stored is what Security Rules match against. Authors (and PI, its last entry) stay free text with roster-backed suggestions (`peopleDatalistHtml()`, a `<datalist>`) — deliberately not switched to a closed picker, since a paper's authors can include people outside this Slack workspace.
   **Only the submitter or a PI/admin can actually save a reassignment (2026-09-11)** — `firestore.rules`' `update` rule requires the `reviewers` map be unchanged unless the writer is `submittedBy.email` or `hasFullWrite()`; an assigned reviewer keeps full write access to everything else on their card, just not to who the reviewers are. **Not enforced client-side**: the picker stays enabled for every signed-in lab member (`reviewerInputHtml()` adds only a `title` hint for a non-owner) — PI/admin status isn't readable by the client (`roles/{roleId}` is deny-all, same constraint as Rush mode's toggle in guideline 6), so disabling it for "not the owner" would also block a real PI/admin who has no other way to prove it. An unauthorized save still fails cleanly via the existing permission-denied toast.
9. **The board card (`renderCard()`) is kept short on purpose.** Title (underlined, so it reads as the click target — `data-open-card`), then only what you need to triage at a glance: status/outcome/overdue badges (the `.card-meta-row` div is omitted entirely when there are none), PI line, reviewer inputs (each with its own tri-state review-status row, Drafted only — see guideline 6), checklist progress, and the Revert/Advance buttons. **Not** on the card: track, the Overleaf link, or edit/remove controls — all of those live on the detail page (track in the grid, "Edit fields" and "Remove paper" in `.detail-controls`). The only `.card-footer` left is the orphaned-status rescue `<select>`. When adding something to the card, ask whether it earns its vertical space or belongs on the detail page.
10. **Board search.** A free-text box plus a field select (Everything / Title / PI / Authors) filter the cards shown in `renderColumns()` — `matchesSearch(card)` does the matching, `boardSearchHtml()` renders the bar (with a live match count), `onSearchInput()` re-renders the whole board on every keystroke but saves and restores the input's focus + cursor position first (a plain `renderBoard()` from an `input` handler would otherwise blur the field the user is typing in). A column with cards that all fail the filter shows "No matches"; a column with no cards at all still shows "Nothing here" — that distinction is deliberate. Resets (`state.search`) on `openVenue()`.
11. **Card detail + gates.** Clicking a card title opens a detail view (`state.view === 'card'`) with all fields and the review tabs (guideline 7) — **Junior = teal, Senior = plum** in the checklist tabs (column headers + `accent-color`). Two independent hard gates, both enforced identically on the render side (`advanceBlockReason()` — greys out Advance and sets its tooltip to the reason) and in `onChangeStatus()` (rejects the move with a toast, whichever route triggered it: Advance button, Revert-button fallthrough, or the status `<select>`):
    - **Checklist gate.** `crossesGate()` blocks any *forward* move from before `GATE_STATUS` (`final_draft`) to it or past it until `checklistComplete()` (both passes complete — 12/12 today) — a card can't leave Drafted for Reviewed until both reviewers are done. `normalizeCard()` rebuilds a stored checklist whose length or labels no longer match `CHECKLIST_TEMPLATE` (a card saved under an older, longer shape), carrying a tick forward only for a part a role had *fully* finished; count-derived UI (`checklistCounts()`, the gate banner's `n/total`) reads the length off the card, so it stays correct without hardcoded totals.
    - **Reviewer-approval gate** (2026-09-11). Same `crossesGate()` boundary, checked right alongside the checklist gate — a card can't leave Drafted for Reviewed until `reviewFilterState(card) === 'approved'` (both `jrReviewState` and `srReviewState` are `'approved'`, see guideline 6). A separate check from the checklist gate, enforced independently — but as of the same day, `onToggleChecklist()`'s auto-sync (guideline 7) means finishing both roles' checklists usually satisfies both gates in one action, unless a reviewer has explicitly flagged `'changes_requested'` (which checklist completion never overrides), so the two can still diverge.
    - **Reviewers-assigned gate.** A card can't Advance into Drafted (from Pitched, normally) unless `reviewersAssigned(card)` — both `reviewers.junior` and `reviewers.senior` set. Only blocks the forward direction; reverting back into Drafted (e.g. from Reviewed) is never blocked by it.
    Add a new gate by extending `advanceBlockReason()` (render side) and adding the matching `isAdvance`-guarded check in `onChangeStatus()` (enforcement side) — keep both in sync, or the button and the toast will disagree.
    `normalizeCard()` migrates older stored cards (status keys — see guideline 6 — plus single-`checked` / `author`-`auditor` / `author`-`junior`-`senior` checklist shapes → `junior`/`senior`, old `auditor` → `senior`, `author` dropped; a legacy `assignedTo` → `reviewers.junior`; `jrReviewState`/`srReviewState`/`outcome`/`authors` default in for cards that predate them, the former from any still-older `changesRequested`/`jrApproved`/`srApproved` shape — see guideline 6; a still-older separate `pi` field is folded into `authors` as the last entry, then dropped).
12. **Venue schedule + .ics.** A venue carries `deadline` (paper), an optional explicit `pitchDay`, and its own dates (`abstractDeadline`, `reviewsPublicDate`, `rebuttalDeadline`, `notificationDate`, `cameraReadyDeadline`). `internalSchedule(v)` returns one chronological list: derived milestones (register −8 wk, pitch, first/final draft, PI approval) then every venue date present. `venueScheduleHtml` renders it as a horizontal timeline (`vs-rail`, one dot per milestone, even-spaced; `short` label + `formatDateShort` date under each); `buildIcs` / `downloadIcs` export it. Keep milestone `key`s stable — they're the `.ics` UIDs.
13. **Venue proposals** (2026-09-11, branch `feature/venue-proposals`, not yet merged). Any signed-in lab member can propose a new venue — the exact same "+ New venue" button and form a PI/admin uses (`venueFieldsHtml`/`readVenueFields`, unchanged) — but `onCreateBoard()` always tries a direct create (`status:'approved'`) first and only falls back to a self-attributed pending one (`status:'pending'`, `proposedBy:{name,email}`) on a permission-denied specifically; there's no client-side "am I admin" precheck to branch on instead (see below). A pending proposal is visible only to its proposer and to PI/admin, via a Security Rules change on `boards/{boardId}` — see `firestore.rules` and `docs/FIREBASE.md`'s "Venue proposals" section for the read-rule shape and why list queries needed restructuring (`fetchVisibleBoards()`, used by both `loadBoardsIndex()` and `saveBoardsIndex()`) rather than the old plain `boards.get()`. `renderVenuesList()` splits `state.boards` into three sections: the normal approved/openable list, "Your proposals awaiting approval" (own pending), and — only when `state.canApproveVenues` (learned from whether the unfiltered pending query itself succeeded, the only way the client can tell it's PI/admin, since roles stay unreadable) — "Pending your approval". **Every row, pending or approved, opens the normal venue page** (2026-09-11, revised same day) — a pending venue's page shows a "Pending approval" badge next to its title, a `proposerLabel()`-rendered "Proposed by Name (email)" line (always both — a name alone isn't enough to tell two proposals apart, same helper used everywhere a proposer is shown), an empty board, and "+ Register paper" disabled. **Approve/Reject appear in two places** (revised again same day, per Eduardo: reviewing shouldn't require a click-in first) — inline in the "Pending your approval" list row *and* in the venue detail page's header, next to Edit venue — both wired to the same `onApproveVenue(id)`/`onRejectVenue(id)`, shown only when `state.canApproveVenues`. `onApproveVenue` flips `status` to `'approved'` (same `saveBoardsIndex` write path and `hasFullWrite()` gate as any other venue edit); `onRejectVenue` deletes the proposal outright (same underlying write as `onDeleteBoard()`, since there's nothing worth keeping — no cards can exist on an unapproved venue, no rejection-reason field in the schema) but has its own confirm/toast wording, and stays visually separate from "Delete this venue" (which now only shows once a venue is actually approved). Approve/Reject are same-size, same-weight buttons (`.btn-approve`/`.btn-reject`, green/red fills) — a deliberately neutral, symmetric either-way pairing, not a primary/plain one that would visually suggest which answer is "correct." Since a pending "Pending your approval" row now has other buttons in it, the row itself can't be a `<button>` any more (invalid HTML) — it's a `<div class="venue-row venue-row--pending">` with its own nested clickable name (`.venue-name-btn`) and Approve/Reject as siblings, not children, of that button. A pending venue's board can't accept a registered paper — "+ Register paper" is disabled as a defense-in-depth backstop (`openModal()`) — since registering to a not-yet-real venue doesn't make sense. **"+ New venue" itself reads "+ Propose venue" for anyone who isn't a confirmed PI/admin** (`updateNewVenueButtonState()`, driven by the same `state.canApproveVenues`, called from `renderAll()` so it stays current once boards load) — the modal's title/submit-label (`openNewVenueModal()`) follow the same split ("Propose new venue"/"Propose" vs. "New venue"/"Create"), same form and `onCreateBoard()` either way. **Before this can deploy**: every board created before this feature has no `status` field — a rule's `.get('status','approved')` covers a single-document read fine, but the new `where('status','==','approved')` query can't match a field that isn't there, so existing venues need a one-time `status:'approved'` backfill (under the *old* rules) before the new rules + query-based loading go live together — see `docs/FIREBASE.md` for the exact sequencing.
