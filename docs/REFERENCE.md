# Reference

Detailed notes on every file and feature, with the reasoning behind them, for anyone editing this project. Start with the root [`AGENTS.md`](../AGENTS.md); search this file for what you're touching. Parts are dated and some describe earlier states of the site.

## What this is

An internal tool suite for BOLD Lab's paper-submission process, built as an **implementation of BOLDiquette § ML Conference Cycle** — and, ahead of BOLDiquette, of the real pre-submission runway the lab runs (register 8 wk out · Pitch Day 6 wk · first draft + Internal Review 4 wk · final draft 2 wk · PI approval 1 wk · submit). A small static site built with Eleventy (no client framework — page bodies are plain HTML, layouts are Nunjucks, client code is plain classic-script JS) plus tracking docs, on a Firebase backend (Firestore/Auth/Storage) as of 2026-09-11.

**Layout, reorganized 2026-09-11:** the served pages and Firebase config stay at repo root (GitHub Pages serves from root; `firebase` CLI expects its config there by default). Contributor-facing docs live in `docs/`.

## Running it

```
npm install          # once
npm start            # build + serve at http://localhost:8137, rebuilding on change
npm run build        # one-off build into _site/
```

Open `http://localhost:8137/how-to-submit-a-paper.html` (or any page). The built site is plain static files with relative URLs, so `_site/` also works under any subpath (it's served at `/bold-os/` on GitHub Pages). Pages that use Firebase (everything gated) need a real `http(s)` origin — Sign-in-with-Slack's redirect flow won't work from `file://`.

**`audit-board.html` talks to real production Firestore by default** (`FIRESTORE_USE_EMULATOR = false`, `AUTH_USE_EMULATOR = false`). For local dev against a disposable local Firestore instead (e.g. testing something that writes data you don't want landing for real): run the Firestore emulator (`firebase emulators:start --only firestore`, needs a JVM — see `docs/FIREBASE.md` for the portable-JDK workaround used when Homebrew's `openjdk` won't install), flip `FIRESTORE_USE_EMULATOR = true` locally, and don't commit that. `AUTH_USE_EMULATOR` can stay `false` even then — the emulator accepts real Firebase Auth ID tokens fine, and the local Auth emulator doesn't have the `oidc.slack` provider anyway. **This flag shipped wrong once already** (committed `true`, silently broke the live site for anyone without a local emulator running, caught 2026-09-11 when a real second user hit it) — double-check both are `false` before committing/pushing. There's now also a loud, hard-to-miss red banner (`#emulatorWarning`/`.emulator-warning`) that shows across the whole page whenever `FIRESTORE_USE_EMULATOR` is `true` — a safety net so a repeat of that mistake would be immediately visible on the live page, not just catchable by re-reading the source. Toggled once, right next to the flag itself, not tied to any render function.

## Deployment

Every push to `main` builds and deploys automatically via `.github/workflows/pages.yml` (Pages source: **GitHub Actions**). Nothing to run by hand. Live at <https://bold-lab-ai.github.io/bold-os/how-to-submit-a-paper.html>.

**New work happens on a branch, not directly on `main`, as of 2026-09-11.** The site is live and in real use now — every feature up to and including this point in the day shipped straight to `main` (each push deploys immediately, and several changes this session also deployed live Firestore Security Rules alongside the client code). From here on: build and commit on a feature branch, get it reviewed/tried, then merge to `main` — merging is what deploys, since there's no separate staging environment. A **Security Rules** change on a branch is not itself live until someone explicitly deploys it (`firebase deploy --only firestore`) — deploying rules and merging the matching client code to `main` should happen together, in the sequence the rules change's own docs/FIREBASE.md section calls for, not the rules going live first on their own.

3. **Copy is terse.** Descriptions (`meta`/OG + hero ledes) are one or two sentences. No throat-clearing, no narrating process or rationale, no knowing-aside / internal-monologue lines. Only what the reader needs to act.
4. Keep an element only if removing it would make the page worse.
5. **Changing phases** (`how-to-submit-a-paper.html`): update the TOC `href`s and labels, each `<section>`'s `id` and `.phase-num`, the `.timeline` rail (`<li>` per phase, `--n` on the `<ol>`, `is-pivot`/`is-after` classes), the pager's static `Phase 1 of N`, and any cross-references (`(Phase 6)`). The JS derives the pager from the TOC hrefs; timeline links are wired via `links.concat(tl)` and synced in `showPhase`.
6. **Board columns mostly mirror the guide's phases — but not one-for-one any more, and worded differently on purpose.** Current `STATUS_ORDER` (7 keys, 2026-09-18+4): `register`, `pitch`, `abstract`, `paper`, `rebuttal`, `camera_ready`, `conference`. `arxiv` stays collapsed into `rebuttal` (2026-09-18+3 — arXiv posting is no longer a gate or a column, just a link addable any time). `paper` was briefly folded into `abstract` that same round, then reinstated as its own stage again (2026-09-18+4, per Eduardo): `abstract` is a lightweight go/no-go now — the senior reviewer (defaults to the PI) approves or requests changes directly, `card.abstractReviewState`, no checklist at all — and only once approved does the card move into `paper` — its button reads "Submit paper" (2026-09-18+7, per Eduardo, was a bare "Advance") but it's still a plain move under the hood, no confirm dialog or green accept styling, gated only by that approval — where the real 12-item Format+Science checklist lives, same mechanism as always, just its own column again. (Don't confuse this button with the OTHER "Submit paper", leaving `paper` for `rebuttal` — same three words, two different actions; see `moveButtonsInnerHtml`'s `rgtConfirmKey`.) The guide (`how-to-submit-a-paper.html`) has **8 phases**, one more than there are statuses: Register, Submit pitch, Submit the abstract (2026-09-18+5: now carries its own "How to review" section covering the senior reviewer's Approve/Request-changes call — the standalone "Wait for approval" phase that used to sit here as its own TOC-only entry is gone, folded into this section instead, since it never mapped to a status of its own anyway), Submit the paper (likewise gained its own "How to review" section, covering the Format+Science checklist), **Post to arXiv** (the one remaining deliberate exception — a real, useful page with no `STATUS_ORDER` key of its own, pulled out of the guide's own Previous/Next pager via `OPTIONAL_IDS`/`steppableIds()` in its inline script, reachable from the TOC but not counted in "Phase N of M"), Submit rebuttal, Submit camera-ready, Accepted. Every other phase still maps to a real status, same order — adding, removing, or reordering one of *those* without the other is still a bug. `RUSH_IDS` (`['phase-1', 'phase-3', 'phase-4', 'phase-6']`) now matches `RUSH_STATUS_ORDER` exactly, one guide phase per real stage — no more TOC-only entries on the rush side to special-case. `STATUS_LABELS` is deliberately **past tense** — Registered, Pitched, Abstract, Paper, Rebuttal, Rebuttal Submitted, Accepted — because a column names the checkpoint already met to be sitting in it (see guideline 11's gates), where the guide's headings are instructional ("Submit pitch", "Submit the abstract") telling you what to go do. Same phase, two label styles for two different jobs; don't try to make them match verbatim. Change `STATUS_LABELS` / `STATUS_HINTS` (the "move a card here when…" line under each column title) text freely. Changing a `STATUS_ORDER` **key** rewrites stored data — any card already at that status is orphaned to the "Other" column. If you must, add the old→new mapping to `STATUS_MIGRATIONS` so existing cards migrate on load — and remember that lookup is a **single hop, not chained**: if an *existing* migration entry targets the key you're retiring, repoint it straight at the new key too (and the reverse holds too: when a retired key comes back as a real stage again, like `paper` did, drop its own migration entry and re-check every entry that used to be repointed past it — `draft_review`/`final_draft`/`pi_polish` moved from `abstract` to `paper` in that same round, since they're semantically about full-draft checklist activity, which is what `paper` means again now) — and, if the old status carried information a rename alone would lose, set the matching field in `normalizeCard()` too (see `STATUS_OUTCOME_MIGRATIONS` and the `changes_requested` case for the pattern). `.columns`' `min-width` (240px × columns + 1px × gaps + 2px border) is computed in `renderColumns()` from however many columns are actually rendering, not hardcoded — Rush mode (below) is exactly why that stopped being a fixed number.
   **Rush mode, added 2026-09-11 — the other deliberate exception.** A per-venue toggle (`board.rushMode`, a one-click button in the venue header, not a field in the Edit-venue form — this is "we need to move fast right now," not a considered edit) that collapses the board to 4 columns (2026-09-18+4, back up from 3 — `paper` reinstated alongside the canonical pipeline's own): Registered, Abstract, Paper, Rebuttal. Not a new status vocabulary — `RUSH_STATUS_ORDER` (`register`, `abstract`, `paper`, `rebuttal`) is a coherent subsequence of the same `STATUS_ORDER` keys, so the checklist gate and `onChangeStatus` need no special-casing at all: full-order indices already answer "did this cross `GATE_STATUS`" correctly regardless of which order a move happened in, since skipping the omitted statuses doesn't change their relative order. `effectiveStatusOrder(board)` picks the active order; `displayStatus(card, board)` is the only place real work happens — it projects a card whose true `status` isn't a column in the active order onto the last one it's actually passed (e.g. a card at Pitched shows under Registered when Rush mode is on), **without ever rewriting `card.status`** — toggling Rush mode is purely a display change, reversible with zero data loss. A card's status only changes when someone actually moves it, and only ever to a value from whichever order was active for that move — so moving a card while Rush mode is on naturally stays within the 4, and flipping back to the full pipeline later just resumes showing/moving through all 7, nothing was ever silently lost. Rush mode's only remaining divergence from the full pipeline is skipping Pitch. Every place that used to read `card.status`/`STATUS_ORDER` directly to compute Left/Right or the status dropdown now goes through `displayStatus`/`effectiveStatusOrder` instead — grep for both if adding a new one.
   Sub-states that used to be their own column aren't columns any more — they're a badge + colour on the card: Drafted's old Ready-for-review / Changes-Requested / Approved split is `reviewFilterState(card)` (three buckets, for the card's colour and the review-status filter) plus `reviewBadges(card)` (what actually renders — can be more than one at once), rendered via `.rv-*` classes and `badge-rv-*`; Reviews Out's old in-progress/submitted split is derived from whether `rebuttalDocLink` is set. Outcomes (Accepted / Rejected / Withdrawn) aren't phases either — they're `card.outcome`, set from the **Edit fields** modal (`eOutcome`), shown as a `badge-outcome-*` wherever the card currently sits — `shouldShowOutcomeBadge()` suppresses it for an Accepted outcome specifically when the card is already in the Accepted column, since showing it there would just repeat the column name.
   **Nothing here is automatic — 2026-09-11, redesigned same day.** Each reviewer has their own tri-state sign-off: `card.jrReviewState`/`card.srReviewState`, each one of `'in_review' | 'changes_requested' | 'approved'` — none derived from `checklistComplete()`. Ticking every checklist box being complete is still the hard gate on advancing past `GATE_STATUS` (`crossesGate`, unchanged), but it no longer means "Approved" by itself — a reviewer has to explicitly say so, and only **that** reviewer: rendered as three buttons, same line, directly under each reviewer's picker in `.card-reviewers` (`reviewStateButtonsHtml(card, role)`, card face and detail page alike), click-enabled only when `state.currentUser.email` matches `card.reviewers[role]` — everyone else sees the same row, disabled, with a tooltip saying so. This is a client-side-only restriction; the Security Rules' card-update condition is still whole-document (submitter/junior/senior/PI-admin, not field-level — see `firebase/firestore.rules`), so it doesn't stop a reviewer from writing the *other* role's field if they bypassed the UI. `onSetReviewState(cardId, role, value)` is the one handler for all six buttons, replacing the short-lived `onToggleChangesRequested`/`onToggleApproval` boolean pair. `reviewFilterState`: `changes_requested` wins if either reviewer is in that state; else `approved` only once **both** are `approved`; else `in_review` (the default, including a partial sign-off). `reviewBadges` shows the fuller picture — a single "Approved" badge once both are, but "JR approved" / "SR approved" individually if only one is. **Auto-advance:** the moment both reach `approved` on a card still in Drafted, `onSetReviewState` moves it straight to Reviewed (`final_draft`) in the same save, still gated by `checklistComplete()` — if the checklist isn't finished yet, the status is left alone rather than skipping that gate; it advances next time a state flips once the checklist catches up, or someone can Advance by hand. **This is also now a hard gate on the manual route** (2026-09-11): `advanceBlockReason()` greys out Advance (and `onChangeStatus()` rejects the status `<select>`/Revert-fallthrough route too) for any move that `crossesGate()` unless `reviewFilterState(card) === 'approved'` — same shape as the pre-existing checklist gate, checked right alongside it, so a card can't leave Drafted for Reviewed by any path until both reviewers have actually signed off, not just ticked every checklist box. The board search bar's second dropdown (`boardReviewFilter` → `state.search.reviewState`, combined via AND with the text query in `matchesSearch`) filters to one of these three buckets — added specifically so "show me everything still needing changes / already approved / still in review" is one click. `normalizeCard()` migrates any card still holding the brief earlier shape (a shared `changesRequested` flag plus independent `jrApproved`/`srApproved` booleans) into the new fields so no reviewer's prior sign-off is lost.
   **A card belongs in a column once that milestone is actually met** — moving it there is an attestation, not a work-in-progress bucket (this is why PI Polish is called **PI Approval**: the column means the PI *has* approved, not that approval is in progress). The title and the hint have opposite tenses on purpose: `STATUS_LABELS` names the checkpoint already met (past tense), `STATUS_HINTS` names what's happening *now*, while the card sits there, or what it's waiting on next (e.g. Registered's hint is "Waiting for pitch", not "Registered") — together they answer both "why is this card here" and "what's actually going on with it." **No confirmation popup on Advance** — there used to be one (`window.confirm()`, a per-status checklist via `STATUS_ADVANCE_CHECKLIST`/`advanceConfirmMessage()`), removed 2026-09-11: native browser confirm dialogs don't reliably appear in every environment, and cards were getting stuck waiting on one that never showed. Moving a card (either direction, through `onChangeStatus`) now just happens — the two *hard* gates (checklist completion before `GATE_STATUS`, reviewers assigned before Draft & Review) are separate, toast-driven checks and are unaffected. Add an entry to both `STATUS_LABELS` and `STATUS_HINTS` whenever a column is added or its meaning changes.
7. **The Internal Review checklist lives entirely in `audit-board.html` now** — `internal-qa-review.html` was a separate, standalone simulated-peer-review page with its own copy of the same 12 items; removed 2026-09-11 since it was redundant with the checklist already on every card (nobody used the standalone page for a review that mattered — the card's checklist is the one that gates Approved). `CHECKLIST_TEMPLATE` (12 entries: `part`, `category`, `label` — 6 format, 6 science, each folding together what used to be several sibling checks) is the only copy left; there's nothing else to keep it in sync with. On a card, each item is `{ id, part, category, label, junior, senior, comments }` — two independent check passes (`REVIEW_ROLES`) plus a per-item feedback thread (see guideline 11). Each card also has `reviewers: { junior, senior }` (each a real person's email — see guideline 8). Assigned **inline on the card face and the detail page** — `reviewerInputHtml()` renders a `<select>`, `onSetReviewer()` saves on change. Deliberately *not* duplicated into the Edit-fields modal — reviewer assignment is meant to be a one-click inline action, not a trip through a form.
   **The detail page's review area is three tabs** — Format, Science, Discussion (`reviewTabsHtml()`, `state.detailTab`, one of `'format'|'science'|'discussion'`, reset to `'format'` in `openCard()`). `checklistTabHtml(card, part)` filters `card.checklist` to one part per tab — same markup as before the split, just one `part` at a time, so `.cl-part` dividers are gone (each panel is already one part). Only the active tab's panel is ever in the DOM (a full string rebuild, not real CSS-hidden panels). Switching tabs is a full `renderCardDetail()`; `onToggleChecklist()`'s partial refresh (gate banner + move controls only, still doesn't touch tab state) is now conditional, not unconditional — see the next paragraph.
   **Ticking a box is restricted to the matching assigned reviewer, and now drives that reviewer's own sign-off automatically (2026-09-11).** `checklistTickAccess(card)` (used by `checklistTabHtml`) disables a role's checkboxes for anyone whose `state.currentUser.email` isn't `card.reviewers[role]` — same client-side-only shape as `reviewStateButtonsHtml`'s tri-state buttons (guideline 6): the Security Rules' card-update condition stays whole-document, not field-level. `onToggleChecklist()` re-checks the same condition itself before writing anything (belt-and-braces against a stray event). Every toggle recomputes each role's checklist completeness and syncs `jrReviewState`/`srReviewState` to match — all of a role's boxes ticked sets that role to `'approved'`; any of them unticked while currently `'approved'` takes it back to `'in_review'` — **except** an explicit `'changes_requested'`, which checklist state never overwrites or clears either way (it's a stronger, separate signal from the reviewer). This can cascade into the same auto-advance-to-Reviewed condition `onSetReviewState` uses (both roles `'approved'`, still in Drafted, `checklistComplete()` — trivially true here since completing the checklist is what triggered this). Because a tick can now change more than the checklist itself (the tri-state buttons, badges, possibly the whole controls row on auto-advance), `onToggleChecklist()` does a full `renderCardDetail()` when the reviewer's own state actually changed or the card auto-advanced, and only falls back to the old gate-banner+move-controls partial refresh on an ordinary tick that crosses no completion boundary.
   **Discussion is a per-card thread, OpenReview-style, one level of replies.** `card.discussion`: array of `{ id, author, authorEmail, timestamp, body, replies }`; a reply (`onPostReply`) is a `{ id, author, authorEmail, timestamp, body }` with **no `replies` field of its own** — that's what caps nesting at one level, there's no UI to reply to a reply. **`author`/`authorEmail` come from `state.currentUser` (2026-09-12), not typed in** — posting requires being signed in (`requireSignedIn()`), same as everything else that needs real identity (`submittedBy`/`reviewers`/`proposedBy`). Older messages posted before this change only have `author` (a free-text name) and no `authorEmail` — anything reading that field (a notification, say) has to handle it being absent. `onPostDiscussion()` appends a top-level message; only the body is required now (no name field to fill in) or the post is rejected with a toast, not silently dropped. Only one reply form is ever open at a time (`state.discussionReplyOpenId`, reset on tab switch and on posting), so the reply input (`#discReplyBody`) can use a fixed id regardless of which thread it belongs to — don't reuse that id for anything else on the page.
   **Every checklist item has its own feedback thread** — same shape and one-level-reply rule as Discussion (including the same 2026-09-12 real-identity change), but scoped to one point (`it.comments`, an array of the same message objects). A checklist row (`.cl-row`) is wrapped in a `.cl-item` with a `.cl-row-foot` toggle beneath it ("Add feedback" / "N comments" / "Hide feedback"); expanding it renders `checklistItemThreadHtml(it)` inline. Only one item's thread is open at a time (`state.checklistCommentOpenId`) and one reply within it (`state.checklistReplyOpenId`); both reset on `openCard()`, tab switch, and (the reply) on posting. Fixed input ids `#clcNewBody` / `#clcReplyBody` — safe for the same reason Discussion's is. Handlers `onPostChecklistComment(cardId, itemId)` / `onPostChecklistReply(cardId, itemId, parentId)` write into `checklist[i].comments`, re-render via `renderCardDetail()` (not the checkbox partial refresh — the thread markup changed), and keep the item's thread open so the reviewer sees it land. `threadCount()` (messages + replies) feeds both the Discussion tab badge and each item's "N comments" label. **Comments never gate anything** — `checklistComplete()` still only reads the `junior`/`senior` booleans; an open concern is a signal to a human, not a hard block. `normalizeCard()` defaults `comments: []` onto any item missing it (and every rebuild path sets it).
8. **Every card has a PI and at least one author — one field, not two.** `card.authors`: array of `{ name, email }` (**changed from plain strings, 2026-09-12** — see below). **No longer required at registration** (changed 2026-09-18+1, per Eduardo, alongside the Overleaf link and the new `abstractText` field below — none of the three are known yet that early): `onAddCard` writes `authors: []`; the registration modal has no author-row UI at all any more. All three become real, gated requirements instead on the transition that actually reaches `abstract` (`advanceBlockReason`'s `toStatus === 'abstract'` checks — `abstractText` itself only joined them at 2026-09-18+8, per Eduardo; it sat as an ungated field for a while first) — filled in via the Edit-fields modal at Submit the abstract, the same modal and the same `authorRowsHtml()`/`renderAuthorRows()` machinery as before, just with only one caller now (`eAuthorsState`) instead of two. **The PI is the last entry in `authors`**, not a separate field (`cardPi(card)` returns its `name`; use `authors[authors.length-1]` directly for the email too); the last row is tagged "PI" (`.author-pi-tag`) and "+ Add author" inserts *before* it, not after, so it stays last as co-authors are added. Detail page shows `authors.map(a => a.name).join(', ')`. **Not shown on the card face** (removed 2026-09-11 to keep the card shorter) — `cardPi()` still backs the "Authors" search scope's PI variant.
   **Authors resolve to a real person's email now, same as reviewers (2026-09-12) — no more free text.** Each row is a `<select>` over `state.people` (the roster), same picker shape as `reviewerInputHtml`, plus a `+ New author (not in the workspace)…` option that swaps the row to two plain inputs (Name, Email) for a genuine co-author outside the lab's Slack — `.author-select`/`.author-new-name`/`.author-new-email`/`.author-use-roster` (switches a row back to the picker) all wired in `renderAuthorRows()`. A row's `isNew` flag is UI-only (which control to render) and is stripped by `authorsForSave(rows)` before the array is ever saved. `authorRowsIssue(rows)` is the Edit-fields modal's validator: the last row (PI) must be a complete `{name, email}`, and no other non-blank row may be half-filled (only possible in "New author" mode — picking from the roster always sets both fields together). **Why this changed:** free-text authors meant the PI had no reliable email to notify (see the Slack-notifications work, `bold-os#1`, branch `feature/slack-notifications`) — same motivating problem `submittedBy`/`reviewers` already solved for their own fields. A "New author" entry is deliberately *not* added to the shared `people` roster (that collection stays a clean sync of real Slack workspace members — see `docs/FIREBASE.md`) — it's stored only on that card. `normalizeCard()` migrates any card still holding plain-string authors to `{name, email: ''}` (email unrecoverable for old data) — a blank email there means a PI-approval notification on an old, not-yet-re-saved card will silently do nothing until someone re-saves the author list through the picker. The senior-reviewer-defaults-to-PI assignment (guideline 6/7) moved from `onAddCard` to `onSaveEdit` for the same reason — there's no PI to default to until authors actually exist.
   **`submittedBy` and the corresponding-author email are set automatically from the signed-in user at registration, not typed in** (2026-09-11) — registering a paper requires being signed in (`requireSignedIn()`). Neither is in the Edit-fields modal: `submittedBy` because it's what Security Rules authorize card edits against, not free-form metadata to reassign; corresponding-author email stays editable there since it's just paper metadata. **Track and the per-card deadline override no longer exist** (removed 2026-09-11) — a card always inherits its venue's deadline; a different track or deadline is a different venue now, by convention. Edit-fields (`openEditModal()` / `onSaveEdit()`) covers title, authors, Overleaf link, **abstract text** (`abstractText`, free text — may contain LaTeX typed as plain `$inline$`/`$$block$$`, rendered on the detail page via `renderAbstractHtml()`/KaTeX, added 2026-09-18+1), corresponding-author email, compute estimate, alongside the always-there post-submission fields (submission link, rebuttal deadline/doc, review notes, outcome). The only things it deliberately doesn't cover: reviewers (inline, see guideline 7), status (the move buttons / dropdown), and the checklist (the matrix itself).
   **Reviewers (Junior/Senior) resolve to a real person's email, via the real Slack roster — not free text.** `reviewerInputHtml()` renders a `<select>` over `state.people` (the `people` Firestore collection, synced from Slack's `users.list` — see `docs/FIREBASE.md`), `value` = email, so what's actually stored is what Security Rules match against. Authors (and PI, its last entry) stay free text with roster-backed suggestions (`peopleDatalistHtml()`, a `<datalist>`) — deliberately not switched to a closed picker, since a paper's authors can include people outside this Slack workspace.
   **Only the submitter or a PI/admin can actually save a reassignment (2026-09-11)** — `firebase/firestore.rules`' `update` rule requires the `reviewers` map be unchanged unless the writer is `submittedBy.email` or `hasFullWrite()`; an assigned reviewer keeps full write access to everything else on their card, just not to who the reviewers are. **Not enforced client-side**: the picker stays enabled for every signed-in lab member (`reviewerInputHtml()` adds only a `title` hint for a non-owner) — PI/admin status isn't readable by the client (`roles/{roleId}` is deny-all, same constraint as Rush mode's toggle in guideline 6), so disabling it for "not the owner" would also block a real PI/admin who has no other way to prove it. An unauthorized save still fails cleanly via the existing permission-denied toast.

10. **Board search.** A free-text box plus a field select (Everything / Title / PI / Authors) filter the cards shown in `renderColumns()` — `matchesSearch(card)` does the matching, `boardSearchHtml()` renders the bar (with a live match count), `onSearchInput()` re-renders the whole board on every keystroke but saves and restores the input's focus + cursor position first (a plain `renderBoard()` from an `input` handler would otherwise blur the field the user is typing in). A column with cards that all fail the filter shows "No matches"; a column with no cards at all still shows "Nothing here" — that distinction is deliberate. Resets (`state.search`) on `openVenue()`.
11. **Card detail + gates.** Clicking a card title opens a detail view (`state.view === 'card'`) with all fields and the review tabs (guideline 7) — **Junior = teal, Senior = plum** in the checklist tabs (column headers + `accent-color`). Two independent hard gates, both enforced identically on the render side (`advanceBlockReason()` — greys out Advance and sets its tooltip to the reason) and in `onChangeStatus()` (rejects the move with a toast, whichever route triggered it: Advance button, Revert-button fallthrough, or the status `<select>`):
    - **Checklist gate.** `crossesGate()` blocks any *forward* move from before `GATE_STATUS` (`final_draft`) to it or past it until `checklistComplete()` (both passes complete — 12/12 today) — a card can't leave Drafted for Reviewed until both reviewers are done. `normalizeCard()` rebuilds a stored checklist whose length or labels no longer match `CHECKLIST_TEMPLATE` (a card saved under an older, longer shape), carrying a tick forward only for a part a role had *fully* finished; count-derived UI (`checklistCounts()`, the gate banner's `n/total`) reads the length off the card, so it stays correct without hardcoded totals.
    - **Reviewer-approval gate** (2026-09-11). Same `crossesGate()` boundary, checked right alongside the checklist gate — a card can't leave Drafted for Reviewed until `reviewFilterState(card) === 'approved'` (both `jrReviewState` and `srReviewState` are `'approved'`, see guideline 6). A separate check from the checklist gate, enforced independently — but as of the same day, `onToggleChecklist()`'s auto-sync (guideline 7) means finishing both roles' checklists usually satisfies both gates in one action, unless a reviewer has explicitly flagged `'changes_requested'` (which checklist completion never overrides), so the two can still diverge.
    - **Reviewers-assigned gate.** A card can't Advance into Drafted (from Pitched, normally) unless `reviewersAssigned(card)` — both `reviewers.junior` and `reviewers.senior` set. Only blocks the forward direction; reverting back into Drafted (e.g. from Reviewed) is never blocked by it.
    - **Abstract-approval gate** (2026-09-18+4, per Eduardo). A card can't Advance from `abstract` into `paper` unless `card.abstractReviewState === 'approved'` — a direct tri-state field (`'in_review' | 'changes_requested' | 'approved'`), not derived from any checklist. Set by the senior reviewer (or anyone signed in — same soft, no-real-access-control pattern as the reviewer picker, since roles aren't readable client-side) clicking Approve/Request changes on the card detail page (`abstractApprovalHtml()`/`onSetAbstractReview()`), shown only while `status === 'abstract'`. Entering `abstract` itself still goes through the authors/Overleaf-link/**abstract-text**/reviewers-assigned gates above (`abstractText` joined them at 2026-09-18+8 — previously just an ungated field).
    - **Paper gates** (2026-09-18+18, per Eduardo). Leaving `abstract` (the real venue submission of the paper — button reads "Submit paper", with the confirm dialog) now also needs `card.submissionLink` (field on the Author tab's "Submit full paper" block). Leaving `paper` (button "Submit rebuttal") needs both reviewers' checklists ticked (`reviewFilterState(card) === 'approved'`, derived as before — no Approve button on Paper) plus `card.rebuttalDocLink` (Author tab's "Submit the rebuttal" block). A reviewer can instead post a checklist point's feedback with **Request changes** (`onPostChecklistComment(..., true)`), which sets their role's `jrReviewState`/`srReviewState` to `'changes_requested'` — the card then reads Changes requested, and the state sticks until that reviewer's checklist is complete again (`onToggleChecklist`). The authors' Format checklist gates Abstract -> Paper, not this. The per-author cap (`abstractAcceptBlockReason()`) is checked at abstract submission — inside `advanceBlockReason()` for `toStatus === 'abstract'`, mirrored in `onChangeStatus()` — not at paper submission. Both pipelines. `outstandingDeadlineFor('paper')` is the venue's **rebuttal** deadline now. In Rush mode the card shows two overdue badges (`overdueBadgesHtml()`): "Review overdue" (reviewer date passed, not approved) and "Submission overdue" (author cutoff passed); outside Rush mode it's the single "Overdue".
