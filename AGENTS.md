# AGENTS.md

How to work on BOLD.OS, the lab's internal site, for anyone changing its code, human or agent.

Live: <https://bold-lab-ai.github.io/bold-os/>. A static [Eleventy](https://www.11ty.dev/) site on GitHub Pages, with a Firebase backend (project `bold-d7ff2`: Firestore, Auth via Slack sign-in, Cloud Functions). The repo is public.

## The rule that decides most things

**Content is edited on the site, not in code.** Everything people read on the site (events, their days and time slots, sessions, talks, skills, …) lives in Firestore and can be added, edited and deleted from the page itself, by whoever the Firestore rules allow. So:

- Don't write content into pages or data files. If you find some hardcoded, the fix is to move it into Firestore and give it add/edit/delete controls on its page.
- A code change is for how the site works: a new kind of content, a new page, a fix.
- Controls a user can't use are shown greyed out with a reason in their tooltip, not hidden.
- Where changes must be reviewed (the how-to guides, BOLDiquette, skills), every change is saved as a proposal, a PI's or admin's too, and a PI/admin other than whoever proposed it accepts or declines it (`decideProposal`, which applies it); nobody changes the content directly. Whoever proposed it can edit it (back into their draft, then **Update proposed change**) or withdraw it while it's open.

**Every automation asks first.** Anything a click sets off beyond the page itself asks before it happens: Slack messages (a DM, a channel, an invite), Google Calendar invitations and their cancellations, emails, Drive sharing, GitHub invitations, and anything else someone might not want. That includes messages a server function sends because of what was saved (a proposal, a comment, a card on the board, a tag), and an agent's action, which tells its person first. So:

- The button calls `BOLD.confirmAction({ title, effects, go })` (`bold.js`) and goes ahead only if it resolves true. `effects` says in plain words what will happen and to whom ("Send every PI and admin a Slack message asking them to review it", "Google Calendar invites BOLD-internal and above").
- **It always asks** (`always: true`, which "Don't ask me again" doesn't skip) when it reaches many people or leaves BOLD.OS: all PIs and admins, a whole group, Calendar invitations, Slack or GitHub invitations, emails, a file anyone with the link can open, releasing or hiding an event.
- Messages to one or two people (whoever a comment or a tag is for, a reviewer, an inviter) ask too, but "Don't ask me again" (`prefs/{uid}.skipConfirm`, back on from the profile) skips them.
- An automation someone may not want is optional (`{ key, text }`, a ticked box): leaving it out is recorded on the object (as a project's workspace `skipped`), and its page offers to run it later.
- Plain edits on the site that tell nobody don't ask. Scheduled reminders the server sends on its own (`remind…`, nudges) are described where people opt in.
- A new automation without its popup isn't finished.

## Layout

```
src/pages/          one file per page: front matter + plain HTML body (.njk if it uses Nunjucks)
src/_includes/      layouts/base.njk + partials/: head, masthead, sign-in gate, sidebar, footer (defined once)
src/_data/site.js   Firebase config, pinned SDK version, sidebar nav
src/assets/css/     bold.css (design tokens, shared components) + pages/<name>.css
src/assets/js/      bold.js (auth, sidebar, shared helpers), pages/<name>.js, shared modules
functions/index.js  Cloud Functions (europe-west2)
firebase/           Firestore and Storage rules, indexes
checklists/         instructions for paper authors' and reviewers' agents (linked by URL from the site; don't move)
docs/               REFERENCE.md (detailed notes per file), FIREBASE.md (backend design), DIFF.md
```

## Run it

```
npm install
npm start          # http://localhost:8137, rebuilds on change
npm run build      # one-off build into _site/
```

**The local site uses the real database.** Signed in on localhost (a popup; the live site uses a redirect), you read and write production data. To try writes safely, use the emulators (they need Java):

```
npx firebase emulators:start --only firestore,functions --project demo-test
```

Or, with nothing real behind it at all: `npm run emulators` (the Firestore and Functions emulators on a demo project, with stand-in secrets).

There is no Auth emulator (Slack sign-in can't run in it). Test rules by calling the emulator's REST API with unsigned tokens (`alg: none`, with an `email` claim and `firebase.identities: { 'oidc.slack': [...] }`: only Slack accounts count as signed in), and seed `roles/pis` and `roles/admins` to give a test user PI or admin rights.

## Developing a Slack feature

Reminders, DMs, buttons, posts in a channel: build them with no access to the real Slack or Firebase.

1. **Build it against a pretend Slack.** `npm run emulators` runs the functions locally; there, every call to Slack is written to the emulator's `slackOutbox` collection (`{ method, args, at }`) instead of sent (`functions/slack-outbox.js`), and answered as Slack would: a channel named in the data exists, a person in `people` has their Slack id. Write test data to the emulator, set off the feature (write the document that triggers it, call the callable, run the scheduled function from the Emulator UI) and check `slackOutbox` for what would have gone out, to whom. A button click is a POST to `slackEvents` with a `payload`, as Slack sends it. To see how a message looks, paste its blocks into Slack's Block Kit Builder.
2. **Send through `pilotSlack(token, key, label, { emails, channel, text, blocks })`** (`functions/index.js`), with a key of the feature's own, not `chat.postMessage` directly, and add the key and its label to `PILOTS` beside it (and to a group in `GROUPS`, `pages/settings.js`, or it shows under Other), so the feature shows under Pilots as soon as it's deployed. Every Slack message BOLD.OS sends belongs to a feature in `PILOTS` or, from before, `LIVE_FEATURES`: pass its key to whatever sends it (`dmByEmail`, `sendEvent`, `postInChannel`, `tellStaff`…). A new feature starts **in pilot**: everything it would send goes to the testers instead, marked with whom it was for, so it can be tried in the real Slack with nobody else hearing a thing.
3. **Open a PR.** Someone with access to the Firebase project reviews it and deploys it. The feature appears under **Settings › Features** (`settings.html#features`); a PI or admin adds you as its tester (or as a tester of every pilot) and you try it for real.
4. **Go live** with the same switch, once it's right: then it messages everyone it's for.

The ground rule still applies: whatever a person's click sets off asks first.

## How pages are built

- **Front matter:** `title`, `description`, `css` (a file in `assets/css/pages/`), `styles` (shared stylesheets in `assets/css/`, before `css`: `["board"]`), `scripts` (files in `assets/js/`), `sdk` (extra Firebase SDKs, e.g. `["firestore", "functions"]`), `permalink` (keep URLs flat: `events.html`), `nav` (the sidebar link to highlight), `area` (its page in the BOLDiquette's Who can see what: who may view it; every gated page has one, and its sidebar entry the same `area` in `site.js`), `areaWhat: "list"` (open to the area's View or Edit: the Projects pages, where Edit without View sees the titles and the projects you're on), `public` (no sign-in gate), `openSignedOut` (no sign-in gate when signed out, the page showing only what's public: the Festival's, `session.html`, `talk.html`, through `public-db.js`), `bare` (no masthead, sidebar or footer: pages for people outside the lab, like `join.html`).
- **JavaScript:** plain classic scripts, each wrapped in an IIFE; no framework, no bundler. Never initialise Firebase yourself: use `BOLD.getApp()`, `BOLD.getAuth()`, `BOLD.onUser(fn)` from `bold.js`. Put any user-provided text through `BOLD.escapeHtml` before it goes into HTML.
- **External scripts:** only the pinned Firebase compat SDK (version in `site.js`), Google Fonts and KaTeX on the board. Ask before adding another.
- **One page per kind of content**, chosen by a query parameter: `event.html?event=`, `session.html?session=`, `talk.html?talk=`, `skill.html?skill=`, `guide.html?guide=`. **Never break a URL**: Slack messages and bookmarks link to them. When one moves, leave a redirect page (see `src/pages/events/old-session-talk-urls.njk`). An event with its own page (`page` on `events/{slug}`: Collaboration Week, the Festival) is linked there (`eventUrl` in functions, `x.page ||` in the pages); `event.html?event=<slug>` forwards to it (`pages/event.js`), since that page can't draw their programme.
- **Who can do what:** clients can't read the role lists. A page asks the `getMyAccess` function whether the user is a PI or admin to decide which controls to enable; the Firestore rules decide what is actually allowed. A PI or admin can **View as** a lower group (the eye button in the masthead): every callable then carries `viewAs`, and the local `onCall` wrapper in `functions/index.js` runs that call as the group (`isFullWrite` false, `access.groupFor` the group). So define callables with that `onCall`, and check the caller with `isFullWrite`/`access`, never `rolesEmails` directly. The same wrapper takes `branch` (the Version button: an open proposal), giving PIs and admins that proposal's Who can see what through `access.table`.
- **Merging proposals:** `functions/merge.js` is shared by the server and the pages (copied to `assets/js/merge.js` by eleventy.config.js). Change it there only, and keep it plain ES5 with no dependencies.
- **Who can see what** (becoming **Who can do what**, DIFF § 17: with the table headed Page | Edit, everyone signed in sees every page, and only acting is by group; letters, introductions, supervision and join requests and their Network links (`privateInteractions`) stay private whoever's group; a field for an outside link shows `BOLD.linkNote()`): the BOLDiquette's part of that name (`access`) is a table of each page's lowest group (Who is BOLD) that may see it and that may change it (at once, or by proposing where changes are reviewed: `REVIEWED` in `functions/access.js`). Accepting a change to it (proposed by whoever has the BOLDiquette's Edit, BOLD-internal and above; accepted by another PI or admin) saves it in `settings/access`, which everything enforces: the rules (`may(page, 'view' | 'change')` on every collection's reads and writes, on top of their own conditions), the callables (`await access.requireAccess(email, page, 'view' | 'change')` after the caller's email), the agents' API (each reading tool and resource names its page) and the pages (`area` gates the page, and its chip at the page's top right opens who can see it, where PIs and admins propose a change; `BOLD.can(area, what)` and `BOLD.cannotReason` for controls). A member's group is their `category`, only PIs and admins set it (PAN-BOLD without one); PIs and admins count as BOLD-exec. A new page or collection takes its area; a new page key goes in `PAGES` in `functions/access.js`, `AREA_NAMES` in `bold.js` and the BOLDiquette's table.
- **Look:** tokens in `bold.css` (cream paper, one navy accent, EB Garamond for reading, Cabin for labels and controls, hairline rules). Match the page you're editing; reuse the shared classes (`.event-form`, `.btn-text`, `.event-controls`, …).
- **Light and dark:** the masthead's sun/moon chooses the theme: Light, Dark or Auto, dark from sunset to sunrise (`mountTheme` in `bold.js`, `src/_includes/sun.js`, kept in `localStorage`). Colours are roles in `bold.css` (`--ink`, `--paper`, `--surface`, `--line`, `--accent` for marks, `--link` for text you can click, `--on-fill`, the hues and the status colours), set once for light in `:root` and once for dark in `:root[data-theme="dark"]`. Write rules with those roles, never a colour value: a tint is `color-mix(in srgb, var(--ink) 12%, transparent)`, a shadow mixes `--shade`. A page can change a role in its own `:root`, and adds a `:root[data-theme="dark"]` block if it wants its own dark value too (`diff.css`). Check both themes. `/theme/` (`tools/theme`, live but not in the sidebar) is the ground truth for how the site looks: every role in light and dark, editable, with the site's components in both and contrast ratios; Export gives the blocks to paste into `bold.css`. A new component goes in its gallery (`gallery-site.html`, `gallery-board.html`).
- **Tagging people:** any textarea offers `@` tags, shown as @Name everywhere and DMed to whoever is tagged by `onTagged`, for any collection. Give a box `.no-tags` when its text leaves BOLD.OS (an abstract, a SKILL.md); add a new collection to `tagPlace` (its link) or `TAG_SILENT` in `functions/index.js`.
- **The + menu:** a page or form people can start (a new kind of thing, a request) gets a row in `CREATE` in `bold.js` (the masthead's + menu), with its `can` check; if its form opens with a click, give the page a link that opens it (`BOLD.takeLinkAction`, as `letters.html#ask`).
- **Markdown fields:** every box people write Markdown in is a `<textarea class="md-field">`, never a page's own: `md-field.js` gives it Write | Preview, the hint and image upload (pasting, dropping or choosing an image or SVG uploads it to the lab's Drive through `markdownImage` and writes `![name](link)`), the same everywhere. Show the text with `BoldMarkdown.render` (`markdown.js`), which shows images (`BOLD.imageHtml`). An abstract is the same field with `data-md="abstract"`. A heading ending ` · 8w`, ` · 10d` or ` · after` is a phase (weeks or days before a deadline, or after it); two or more draw a timeline before the first (`markdown.js`, `.md-timeline`), as in the BOLDiquette's ML Conference Cycle.
- **Comments:** a new kind of comment thread belongs on `comments.html` (`pages/comments.js`), and every Slack message about a comment links to the comment itself, not just its page (`#c=` on a guide, `&msg=` on the board).
- **Search:** a new kind of content gets a section in `BoldSearch.SCOPES` (`search-box.js`) and a loader in `LOAD` (`pages/search.js`), and the same in the agents' `search` tool (`functions/api.js`); both rank with `search-rank.js`.
- **Agents:** `functions/api.js` lets people's AI agents read BOLD.OS as them (MCP and JSON, personal tokens from their profile; activity on `agents.html`), and act as them once a PI or admin approves (Requests → Agents). Anything it returns must match what that person sees on the site, and never include email addresses. A new feature gets its action in `functions/api-actions.js`, doing what its page does: Firestore writes as the person under the rules (`asUser`), callables through the callable (`act`); never admin writes that skip the rules. The site is the single source of truth for what agents get: instructions are the BOLDiquette's Agentiquette part, word for word (after one line in code, `FLOOR`, that puts the BOLDiquette first), prompts from the skills, resources from the pages, and added tools from the Tools pages (`agentTools`, changed by proposals like everything else); added tools run only in `mcpSandbox` (no roles, no secrets, as the caller), never in BOLD.OS's own functions. Never give the MCP content of its own.
- **Automations ask first:** see the ground rule at the top (`BOLD.confirmAction`).
- **Notifications:** anything someone should hear of goes to their Inbox (`notifications.html`) through `deliver(emails, { text, href, feature, source, about })` (`functions/index.js`), never a Slack DM of its own: Slack only pings them that there's something new (pilot `notification-pings`). What someone is part of (projects, cards, parts, skills, tools, editions) is in `functions/notify.js`: a new kind of thing with people in it gets its notifications there.
- **Boards:** anything shown as columns of cards uses the shared board, `BoldBoard` (`assets/js/board.js`, styles `board.css`): `searchHtml`/`wireSearch` for the search bar above it, `columnsHtml` for the columns (as wide as the Internal Review Board's, scrolling sideways), `equalizeHeads` after each render (every head as tall as the tallest), `paged` and `onMore` (20 cards a column, then Load more), `.board-card` on each card, `drag` to move cards between columns by dragging (mouse, or holding a card on a touch screen). The Internal Review Board and a project's Board tab both use it.
- **Left edge:** every page's content starts at the same place: that of a 900px column centred beside the sidebar (`--content-max`, `margin:0 auto`). A guide keeps that edge with its contents on the right (`margin-left:var(--page-left)`, bold.css; never its own `auto` centring). A board stays in the page's column except the board itself (its search and columns), which is wider and centred under the column: as on a project's Board tab (project.css `.wk`) and the Internal Review Board.
- **Copy boxes:** any text offered for copying uses `BOLD.copyBoxHtml(text)`: a code box with the clipboard icon inside it. Never a text "Copy" button.
- **Page copy is terse:** one or two sentences of description, no commentary about the process or the code.

- **Emails are lower case everywhere**, keys and fields alike; Slack's own case is lowered when `people` syncs (`upsertPerson`, `syncPeopleFromSlack`). Compare emails lower-cased. `people` holds only our Slack workspace's members: users from other workspaces in shared channels (their `team_id` isn't ours) are left out, as their ids can't be invited to our channels (`user_not_found`).
- **Every request and board card has a number** (#123, one sequence: `numberFor(path)` in `functions/index.js`). A new kind of request is numbered where it's made, and its Slack message starts with it (`numberTag`).
- **Every write path needs a rule** in `firebase/firestore.rules`. Test new rules in the emulator, both what should pass and what shouldn't.
- **Version history:** each write to a tracked collection is saved as a full copy in `<doc>/versions` by a server function, and `history.js` shows versions, changes and Restore on the page. To track a new collection: add it to `TRACKED` in `functions/index.js`, require `updatedBy == email()` in its rules and let readers read `versions`, write `changeNote` on save, and mount `BoldHistory` on its page. `skills`, `guides` and `handbook` are tracked so far.
- **Functions** run on Node 22 (`engines` in `functions/package.json`).

## Adding a feature

Building a feature (a page that reads and writes its own data, say a rota) needs no keys and no access to the Firebase project:

- **No API key.** The Firebase web config in `src/_data/site.js`, its `apiKey` included, is public: it names the project and grants nothing. People write as themselves, signed in with Slack, and the rules decide what they may do.
- **In the PR:** the page and its script, its Firestore collection, the rules for it in `firebase/firestore.rules` (behind `isSignedIn()`/`isLabMember()`; who may manage it as a rule of its own, such as a list it checks, rather than making them site admins), and any server work (reminders, schedules, Slack messages) as functions in `functions/index.js`, using the secrets already there (e.g. `SLACK_BOT_TOKEN`) without seeing them.
- **Test in the emulators** (see Run it): they need no access to the real project.
- **Unit tests:** `npm test` runs `tests/*.test.cjs` (Node's built-in runner, nothing to install). Give a fixed bug a test there, on its pure parts: a server function in `functions/index.js`'s `_internal`, a page's logic as a plain function in its own file under `src/assets/js/` (loaded with `vm`, as `tests/projects-join.test.cjs` does).
- **Deploying:** someone with access to the Firebase project reviews the rules and deploys them, and any functions, when the PR merges.
- **Don't give contributors rules access** to deploy their own. The rules are one file for the whole database, so whoever deploys them can change any rule; reviewing them is what keeps data from leaking or being overwritten.
- **No service-account keys.** A tool that ran outside the site with its own key becomes a page or a function here; no key leaves the project.

## Shipping

- **Plan on the board:** BOLD.OS's own work, code and content, is on the BOLD OS project's **Board** tab. Add a card for what you take on, put yourself on it, and link it to its pull request or proposed change: it then moves along with it. **Move every card you work on as you go**: to Doing when you start, to Review when it's waiting on someone (a pull request, a proposal to accept, a push to approve), to Done once it's live. A card linked to its pull request or proposal moves by itself; any other card you move yourself, on the board or with the MCP's `work` tool (`action: move`, `column`: `doing`, `review` or `done`). Each card has its own page (click its title) for a description and images.
- **Pull requests:** work on a branch and open a PR to `main` (one approval needed). **Merging deploys the site** through GitHub Actions; there is no staging site.
- **Rules and functions deploy separately**, by someone with access to the Firebase project:
  - `npx firebase deploy --only functions:<name>` and `npx firebase deploy --only firestore:rules`, with `--project bold-d7ff2`.
  - **Never a bare `firebase deploy`**: production runs functions that aren't in this code.
  - Deploy rules together with the client code that needs them.
- **Never enable Firebase Hosting** on the project: it breaks sign-in.
- **Only Slack accounts count.** `isSignedIn()` in the rules and `signedInEmail` in the functions require a Slack identity on the account (`token.firebase.identities`, not `sign_in_provider`, which linking GitHub changes), and `onlySlackSignUps` refuses any new account that isn't a Slack one; together another provider, such as GitHub, never gives access on its own. Keep any new rule or callable behind them.
- **Sign-in:** don't change how it works without testing in private windows on desktop and phone. The setup and its history are in `docs/REFERENCE.md` under "Sign-in".
- **Public repo:** no secrets, tokens or people's email addresses in code or docs. Role lists live in Firestore.

## The lab's Google account

Project meetings, slides and notes, students' meetings with their supervisors and the welcome email to new members go through the lab's Gmail account (`GOOGLE_OAUTH`; `docs/REFERENCE.md` under "Project workspaces" says how to reconnect it). It owns every file and meeting it makes. A new function that uses it lists `GOOGLE_OAUTH` in its `secrets`.
